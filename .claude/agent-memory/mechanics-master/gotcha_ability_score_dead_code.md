Found while inventorying every STR/DEX/CON/INT/WIS/CHA touchpoint for a proposed six-attribute redesign (2026-07-29, diagnosis-only, no code changed). These are dormant/dead paths worth knowing before tracing any ability-score-related bug or doing the eventual rename:

- `Combatant.makeSavingThrow(ability, dc, options)` in `src/systems/CombatManager.js` (~line 2858) is a fully generic, proficiency-aware saving throw method — but it has **zero callers** anywhere in `src/`. Actual save resolution in live combat goes through separate, narrower paths instead: `EffectDispatcher.rollDefenderSave()` (maneuver saves, no proficiency), the inline CON-only Topple mastery check in `CombatManager.js` (~1518-1521, no proficiency), and the regex-parsed `executeSpecialMonsterAction` save (~line 740-751, parses `DC \d+ (STR|DEX|...)` out of the monster's free-text `description` string in `monsters.json`). None of these three live paths apply saving-throw proficiency; `character.savingThrows[ability].proficient` (built by `Character.initializeSavingThrows()`) is effectively unused by real combat resolution.
- `RULES.callingResources.resolve` in `src/core/rulesEngine.js` (~line 585-595, formula `'con_mod + level'`) is never read by any system file — `Character.calculateMaxResolve()` hardcodes the same formula independently instead of consuming the RULES entry. Two sources of truth, only one is live.
- `CombatManager.castSpell()` is a stub (`"Spells not yet implemented"`). Everything in `data/spells.json` (savingThrow, concentration, spellcastingAbility usage) and `Character.spellcasting.spellSaveDC`/`spellAttackBonus` is computed but only ever displayed on the character sheet (`main.js` ~6157/6161) — not consumed in combat. Scholar and Wanderlust are marked "COMING SOON" in `classes.json`. Concentration checks (`RULES.spellcasting.concentrationCheckDC`) have no implementation anywhere.
- Monster `abilityModifiers` (the `(score-10)/2` formula) is duplicated inline in **three** places instead of calling `getAbilityModifier()` from `src/utils/dice.js`: `Character.calculateAbilityModifiers()` (uses the shared helper, correct), `EncounterBuilder.js` buildMonsterCombatant (~line 183-190, inline reimplementation), and `Player.js` (~line 1678-1685, inline reimplementation, appears to be a legacy/parallel encounter path). Any formula change to ability-modifier math needs all three updated.
- Skill-to-ability mapping is duplicated: `data/skills.json` has the canonical `ability` field per skill, but `Character.js` `updateSkillBonuses()` (~line 364-378) has a second, hardcoded `skillAbilities` object mirroring it rather than reading from the skill data. `SkillChallengeManager.getSkillModifier()` (~line 502), by contrast, reads `skillData.ability` generically off a `character.skills` **array** — a third, differently-shaped skills representation from the same character.
- `data/monsters.json` `savingThrows: { wis: 0 }`-style fields (5 monsters have them) and `data/backgrounds.json` `abilityScoreIncreases` arrays are both unread by any code path found — likely dead/aspirational data.

Why this matters: before diagnosing any ability-score interaction bug, check whether the code path involved is actually one of the live ones above, or one of the dormant/duplicate ones — a fix to the "obvious" generic function (e.g. `makeSavingThrow`) may have zero effect on observed behavior because nothing calls it.
