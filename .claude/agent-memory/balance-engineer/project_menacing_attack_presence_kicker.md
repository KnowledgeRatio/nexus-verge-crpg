`game-designer` proposed retrofitting Menacing Attack (`data/abilities.json:123-145`, Dedication/Exemplar L3, `onHitSaveOrCondition` frighten effect, `EffectDispatcher.js:458`) with a Presence kicker on its save DC: `8 + prof + Prowess_mod + floor(Presence_mod/2)`, resisted by the plan's already-locked Composure save. Not yet in `docs/plans/2026-07-30-attribute-system-remap.md` — still under review as of this pass.

**Verdict on the 4 questions asked, evidence-based:**

1. **DC delta, real point-buy + real (corrected, see [[reference-asi-every-level-not-asilevels-gated]]) ASI progression, L3-L10:** a genuinely "invests alongside Prowess" dread-knight (alternates ASIs Prowess/Presence) sees DC delta of **+1 at L3, +0 at L4-6, +1 at L7-9, +2 at L10** vs a pure-Prowess baseline. The degenerate "abandon Prowess entirely, max Presence" build (all ASIs into Presence, Prowess frozen at chargen 15) never exceeds baseline and falls **-1 behind from L6 onward** — the halved-and-floored kicker structurally cannot compensate for Prowess's own full-weight, still-growing contribution to the same formula. No dominance-inversion found; max real-world swing is +2 DC at L10, a small tail.

2. **CC-uptime / win-rate risk (real 500-trial Monte Carlo per cell, L3/5/7/10, favorable+unfavorable monsters):** win-rate deltas between dread-knight and pure-Prowess builds were **+0.0 to +2.4 winRate points** in every non-boss matchup, and actually **-1.6 points** (dread-knight worse) in the L10-vs-boss (voidTitan) matchup — because the dread-knight's opportunity cost (less Prowess growth, thus lower damage) roughly offsets or exceeds the extra frighten-uptime benefit. Frightened uptime itself was already high for BOTH builds in mid/high-CR fights (56-95%) **before** the kicker is even applied — this is a pre-existing characteristic of Menacing Attack's generous Resolve economy (`con_mod + level`, easily enough to spam the maneuver almost every hit in a normal-length fight), not something this proposal creates. If frighten-uptime is a concern, the root cause is the Resolve pool size / maneuver-spam economy generally, not the Presence kicker specifically. Verdict: **safe, no disproportionate uptime/win-rate problem from the kicker itself.**

3. **"Zero regression at Presence 0" claim: FALSE for the realistic case.** The claim only holds at the literal narrow window Presence mod = 0 (score 10-11). Point-buy's floor is **score 8** (`RULES.core.pointBuyCosts`, cheapest/default value for an untouched stat), which gives mod **-1**, and `Math.floor(-1/2) = -1` in JS — so a build that dumps Presence to the point-buy floor (the *rational, expected default* for a pure-Prowess Exemplar, since the plan's own decision #1 already establishes Presence is otherwise inert for Dedication) gets a DC **one point worse than today's unmodified formula**, not the same. Confirmed both arithmetically and in the sim harness (`PresenceDumped8` scenario, consistent -1 DC at every level tested, L3-L10). This is a real, if small, regression the proposal's framing does not currently acknowledge. **Recommend to `game-designer`/`backend-dev`: clamp the kicker non-negative, e.g. `Math.max(0, Math.floor(Presence_mod/2))`, if "zero regression, pure upside" is meant to be a hard guarantee rather than "true only near mod 0."**

4. **Other risks flagged, not raised in the original proposal:**
   - **Precedent pressure:** Trip Attack, Pushing Attack, and Disarming Attack share the exact same base `maneuverSaveDC()` formula and sibling `onHitCondition`/`onHitPush` handlers. Giving only Menacing Attack a second-stat kicker breaks DC parity across the four Exemplar on-hit maneuvers and creates a natural "why not Trip/Push/Disarm too" ask later — worth deciding now whether this is meant to be Menacing-Attack-specific forever (thematically defensible: fear is the one condition-flavor plausibly tied to force-of-personality) or the first of a wave.
   - **Player/companion ASI asymmetry** ([[reference-asi-every-level-not-asilevels-gated]]): player characters get 9 ASI events by L10, companions get 2 (gated by `RULES.progression.asiLevels`). A companion-piloted Dedication Exemplar can never plausibly reach the dread-knight build's Presence investment level in the same timeframe — the kicker is meaningfully weaker in practice on companion-controlled combatants. Not a balance bug (companions using the SAME formula just can't invest as much), but worth game-designer's awareness if companion parity with the player build matters here.
   - **Implementation shape is clean per ADR-010**: the proposed `dcBonus: {stat, divisor}` field on the generic `onHitSaveOrCondition` handler, defaulting to absent/no-op, is genuinely additive and doesn't touch Trip/Push/Disarm's JSON — confirmed no `if (ability.id === ...)` branching required.

**Composure defender-save modeling note (hypothetical, no live analog):** monsters have no Composure field yet (six-attribute system unbuilt). Simulated as `floor((rawMod(wis) + rawMod(cha)) / 2)` per the plan's own decision #2 ("average the two") + the plan's "engine rule" (sum raw fractional, floor once) — applied to plain ability scores since ordinary (non-dragon) monster blocks have no separate structured save-bonus field to average directly. Documented as a hypothesis-testing proxy, not a locked mapping — future monster-data remap work should re-derive this properly once Composure is a real field.

Harness: `tools/balance-sim/menacing-attack-presence-kicker-sim.js` (500 trials/cell, levels 3/5/7/10, NaN-safe monster list per [[reference-monsters-abilities-nan-bug]]). Reusable for any future Exemplar-maneuver DC-kicker proposal — the `menaceDC()` / `resolveManeuverDieSides()` helpers are formula-agnostic enough to retarget at Trip/Push/Disarm if that precedent-pressure risk (point 4 above) materializes.
