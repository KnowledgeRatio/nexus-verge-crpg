Requested by `game-designer` as the last M2 step of `docs/plans/2026-07-30-attribute-system-remap.md`, after M2's monster/race/class/background/kit data conversion completed and a data-loss incident (19 monsters' `abilities` briefly reverted to `[]` by a stray `git checkout`) was fully recovered and re-verified (417/417 tests, 0 empty abilities). This pass validates the CONTENT, not the mechanism — [[project_attribute_remap_m1_5_fix_verification]] already confirmed the formulas/wiring are correct; this pass checks the full 46-monster bestiary and full chargen for balance regressions now that real content exists everywhere.

**Verdict: safe to ship.** All 4 requested checks pass. Two bugs found are both pre-existing and orthogonal to the remap (not caused by it, not gating M2).

## Point 1 — CR/DPR sanity across the bestiary: PASS

Proven **by construction, not sampling**: `data/monsters.json`'s `abilitiesSixAttribute` field is a straight 1:1 bijective copy of the legacy `abilities` block (str→prowess, con→vitality, int→intellect, dex→insight, wis→composure, cha→presence) for all 46 monsters, verified programmatically. Since monster AC and HP are flat data fields (untouched by the remap) and attack bonus/save bonus are single-attribute lookups under this bijection, sixAttribute-mode combat stats are mathematically forced to equal legacy-mode stats — confirmed via the real `getAttributeModifierFor()` and real `CombatManager.calculateMonsterAttackStats()` for all 46 monsters (attack bonus, composureSave mod, vitalitySave mod all compared, 0 mismatches, including all 19 recovered monsters individually).

**The 19 freshly-authored (data-loss-recovered) monsters, cross-checked against published SRD stat blocks by hand:** 17/19 match their SRD ability scores exactly (ghoul, specter, ghast, gargoyle, wight, owlbear, flameskull, ettin, troll, wraith, youngWhiteDragon, youngRedDragon, manticore, mage, medusa, shadow[WIS differs], youngGreenDragon[CON off by 1, dragons already flagged non-canon]). Two CR-inert deviations found:
- **minotaur: WIS 20 vs SRD 16.** Feeds Composure (+5 not +3). Internally consistent with the monster's own pre-existing `skills.perception: 7` (7 = WIS20mod(+5)+prof(+2); SRD's WIS16 would only give +5) — looks like a deliberate choice to keep an already-shipped skill number coherent, not a slip. Real effect: minotaur resists Composure saves ~2pts better than SRD CR3 suggests; narrow exposure since only 1 live WIS-saveType ability exists today.
- **hillGiant: INT 3 vs SRD 5.** Feeds Intellect, which has zero consumer for this monster (no Intellect-keyed skill, non-caster). Functionally inert, no gameplay effect.

Neither deviation is CR-relevant (doesn't touch attack bonus, AC, HP, or damage) and neither needs a fix — noted for completeness, not flagged as an action item.

## Point 2 — "Insight is the free third stat" (decision #1) re-test: unchanged, still bounded

Structurally confirmed unchanged: `Character.calculateAC()` still gates evasion (Insight) behind `armor.addDexModifier`, and `chainMail` (Dedication's starting armor) still ships `addDexModifier: false`. The evasion/soak AC split this risk depends on is still unbuilt — the mechanism is exactly as bounded as [[project_attribute_remap_saves]]'s earlier small-sample finding, not newly realized now that full chargen/bestiary exist.

Re-ran the dump-dominance Monte Carlo at full scale (real `Character` construction via real chargen-shaped Dedication build, real `CombatManager.attack()`/`executeMonsterAttack()`, full `monsters.json` bestiary, sixAttribute mode, 500 trials/cell, L1/5/10 × favorable/unfavorable): Balanced beats ProwessDump by **+4.4 to +53.0 win-rate points** in every non-degenerate matchup (the one 0%/0% cell, L10 vs voidTitan, is both builds losing to an out-of-bracket CR10 boss regardless — not dominance, no signal). Same shape and magnitude as the earlier small-sample finding — confirms it holds at full scale.

## Point 3 — zombie/mage save-averaging fix, in actual encounters: PASS

Ran the real `EffectDispatcher.execute()` `onHitSaveOrCondition` path (not the deterministic isolated call from the prior fix-verification pass) with live `Math.random()`, 500 trials/cell: Trip Attack (vitality save) vs zombie at L3/L7, Menacing Attack (composure save, via the `wis`→`composureSave` legacy-key redirect) vs mage at L5/L10. All 4 cells land strictly between 0% and 100% apply-rate (33-52%), confirming the hand-authored `savingThrows` overrides (zombie composure=0, mage composure=4 — both averaged/passthrough correctly per [[project_attribute_remap_m1_5_fix_verification]]) produce sane, non-degenerate resistance in a live dispatch chain, not just in the isolated formula check.

## Point 4 — general sweep: PASS, no degeneracy

Full round-based Monte Carlo via real `CombatManager.attack()`/`executeMonsterAttack()`, real `Character`-built Dedication PCs (L1/5/10), real monster data, 500 trials/cell, legacy vs sixAttribute mode side by side. Every matchup's legacy-vs-sixAttribute win-rate delta is statistically indistinguishable (all deltas -3.4 to -0.4pts, well inside each cell's ~6-9pt CI margin sum) — confirms the six-attribute conversion introduces no win-rate regression anywhere in the tested matrix, matching the "proven by construction" result from point 1.

## Two orthogonal bugs found, unrelated to the remap — reported, not fixed (backend-dev territory)

1. **`weapon.damage.dice` shape mismatch (CombatManager.js:~1101-1108), likely significant.** Every weapon in `data/items.json` stores `damage` as a plain dice-notation string (e.g. `"1d8"`), but `CombatManager.attack()`'s hit-damage-roll code reads `weapon.damage.dice` (expects an object). Since `"1d8".dice` is `undefined` in JS, the code silently falls through to the unarmed-strike default (1d4) for **every equipped weapon in live gameplay**, regardless of the weapon's real die. Verified with a direct 200-trial repro against real `items.json` + real `CombatManager.attack()`: observed damage range matched 1d4(+bonus)/2d4(+bonus)-on-crit exactly, not the expected 1d8/2d8 range for a longsword. The existing unit tests in `tests/systems/combatManager.characterization.test.js` don't catch this because their hand-written weapon fixtures use `damage: { dice: '1d8' }` (the shape the code expects), which is NOT what `items.json` actually contains — the test fixtures and the real data have silently diverged in shape. This affects legacy and sixAttribute mode identically (not attribute-keyed), so it didn't bias any comparison in this pass, but it means every player weapon-attack DPR number in this game today is running well below intended values. Flagged to `backend-dev`, not fixed here (orthogonal to this remap task).
2. **`calculateMonsterAttackStats()` (CombatManager.js:539) crashes on `action.damage` shaped as an object.** The five "void"-family monsters (voidTrace, voidSpawn, voidHunter, voidShaper, voidTitan) have non-weaponId attack actions whose `damage` field is `{dice, bonus, type}` rather than a string; line 539's `(action.damage || '1d4').match(...)` throws `TypeError: ...match is not a function` on that shape. Confirmed via direct real-code repro. Also orthogonal to the remap (pure data/code shape mismatch), affects both modes identically. Not yet confirmed whether this code path is actually reachable in live play for these monsters' primary attacks (some void abilities may route through a different AoE/special-effect path that never calls `calculateMonsterAttackStats`) — flagged for `backend-dev` to trace and confirm reachability, not asserted as a live crash without that check.

## Separately noted, not a balance issue — inert/write-only data and code gaps found as a byproduct

- **`EncounterBuilder.js`'s `createEnemyFromMonster()` never reads the native `abilitiesSixAttribute` field** — it still derives sixAttribute-mode monster abilities at runtime via `convertLegacyAbilitiesToSixAttribute(monster.abilities)` from the legacy block. Harmless (the two are mathematically identical, verified above), but means the M2 batch-conversion work on `abilitiesSixAttribute` is currently write-only data with zero code consumers. Low-priority architecture note for `backend-dev`/`architect`, not a bug.
- **`Character.js`'s `initializeSavingThrows()` (line 480) never branches on `RULES.attributes.system`** — it always loops the legacy 6 abilities and checks proficiency against `this.class.savingThrowProficiencies` (the legacy field), never `savingThrowProficienciesSixAttribute`. In sixAttribute mode, Dedication is computed as proficient in *both* the (retired, never-rolled) Prowess-save and Vitality-save, instead of Vitality-save only per the locked "one proficiency per calling" decision. **Zero combat-balance impact** confirmed — no live ability ever triggers a Prowess-save roll (it's fully retired, matching Intellect-save's situation), so this never changes an actual dice outcome. It IS a character-sheet-display/data-correctness gap relative to the locked design (would over-report save proficiencies in UI). `savingThrowProficienciesSixAttribute` (`data/classes.json`) has zero code consumers anywhere in `src/` — same "write-only data" shape as the `abilitiesSixAttribute` monster field above. Flagged for `backend-dev`; not a blocker for this validation pass since it doesn't move any win-rate or DPR number.
