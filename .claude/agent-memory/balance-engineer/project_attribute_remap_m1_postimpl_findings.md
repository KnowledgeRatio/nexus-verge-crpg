M1 step 7 (lightweight balance pass after formulas landed, before M2 content work) found two implementation bugs in `docs/plans/2026-07-30-attribute-system-remap.md`'s built code that the design-stage simulations (necessarily reimplemented math, no code existed yet) could not have caught, and that the M0/M1 unit test suite (`tests/systems/combatManager.characterization.test.js`, `tests/systems/effectDispatcher.sixAttribute.test.js`) also missed because the tests were written to match the implementation, not the design doc's formula text.

**Finding 1 — `getBlendedAttributeModifier` never divides by attribute count.** `src/utils/attributeResolver.js:125-138` sums raw modifiers across a blend's attributes and floors once — it never divides by `entry.attributes.length` (or by 2). Decisions #3 (concentration), #4 (flee), #5 (Menacing Attack DC) all state the formula literally as `floor((A_mod + B_mod) / 2)` — an average. The plan's own "Engine rule" worked examples (the ones the implementer cited in the resolver's docstring) never carry through the `/2` step either, so the bug is consistent with the plan's own worked examples and got baked into the unit tests' expected values (`effectDispatcher.sixAttribute.test.js:112-125`'s test title says ".../2)" but its expected value is the un-divided sum). Net effect confirmed by real-code Monte Carlo: Menacing Attack DC deltas are a flat **-1** for pure-Prowess at every level (not the design-approved escalating -2/-3/-3/-3) and **+3 to +4** for Balanced (not the approved near-neutral -1/-1/0/-1) — Balanced's frighten-uptime lead over pure-Prowess is 17-24 points, not the 5.7-15.6 points that was explicitly signed off as "the intended bite of convergence." Single-attribute contexts (`getAttributeModifierFor`, e.g. Trip/Push/Disarm's shared meleeAttack DC) are unaffected — this is blend-only.

**Finding 2 — no code path anywhere populates six-attribute-keyed `character.abilities`.** `Character.calculateAbilities()`/`baseAbilities` (`Character.js:26-33,183-198`) and `EncounterBuilder.createEnemyFromMonster()` (`EncounterBuilder.js:183`) both construct `abilities` with legacy keys (str/dex/con/int/wis/cha) **unconditionally** — not gated on `RULES.attributes.system`. `attributeResolver.js`'s `resolveAbilityKey()` only redirects new-system keys to legacy keys when `system === 'legacy'`; in `'sixAttribute'` mode it passes new keys through unchanged, assuming the character already carries six-attribute-keyed data. Nothing produces that shape today. Confirmed via real `Character`/`CombatManager.flee()`/`EffectDispatcher.execute()` with the flag flipped: every attribute-derived modifier (attack, AC evasion, initiative, all saves, flee, Menacing DC) silently resolves to 0 for every player character AND every monster the instant the flag flips — not a monster-only "content volume" gap, universal. This is missing from the plan's M1/M2 execution order as a named step.

**Smaller Finding 3 — monster save-shim output has zero consumer.** `convertMonsterSavingThrows()` (`src/utils/monsterAttributeConversion.js`) correctly averages a monster's WIS+CHA save-bonus overrides into `enemy.savingThrows.composure`, but `rollDefenderSave()` (`EffectDispatcher.js:468-472`) reads `defender.character.abilities.composure` only, never `.savingThrows`. The shim's averaging math is correct; its output is orphaned. Currently moot given Finding 2, but will remain dead even after Finding 2 is fixed unless something is wired to prefer a monster's explicit save-bonus override over the flat ability-modifier path.

**Why this matters:** the plan's M1.5 flip criterion ("Named sign-off checkpoint before flipping the default flag") and its "M2 doesn't block the flip" framing both assume the flag can be safely flipped for a playtest once M1's formulas land. Findings 1 and 2 mean flipping today would produce broken/miscalibrated combat, not a soft content gap.

**How to apply:** don't treat M1 step 7 as clear-to-flip. Recommend to `backend-dev`: (a) fix `getBlendedAttributeModifier` to divide by `entry.attributes.length`, re-verify against decisions #3/#4/#5's literal formulas, and correct the now-wrong unit test expected values; (b) add a named step converting `Character.js`/`EncounterBuilder.js` ability-key population to six-attribute keys, gated on the flag, before M1.5's sign-off checkpoint — not folded into M2's monster-content-volume framing. Re-run the harness below after both land; expect the Menacing DC delta table and flee dump-punishment numbers to shift.

**Harness:** `tools/balance-sim/attribute-remap-post-implementation-sim.js` — calls the real `attributeResolver.js`, `CombatManager.flee()`, and `EffectDispatcher.execute()`/`maneuverSaveDC()` directly (dynamic imports + a stubbed `Audio` global, since static ESM imports would construct `AudioManager` before any headless stub could apply). 600 trials/cell. Reusable for re-verification once both findings are fixed — rerun and diff against this memory's numbers.
