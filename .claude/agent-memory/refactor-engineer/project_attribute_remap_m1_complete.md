`docs/plans/2026-07-30-attribute-system-remap.md` M1 step 5 (refactor-engineer swaps `.str`/`.dex`/etc. call sites to `attributeResolver.js` functions, `RULES.attributes.system` staying `'legacy'`).

**Attempt 1 (2026-08-01, morning):** fully blocked — `attributeResolver.js` had no legacy-mode key translation, every call returned 0. Fixed upstream by backend-dev before the retry. See [[feedback_verify_plumbing_before_wiring]].

**Attempt 2 (2026-08-01, retry):** partial completion. Skills/AC/initiative wired byte-identical, test-verified. Saves and attack resolution (melee/ranged/finesse) escalated as blocked — `derivedStatMap` only had target-system shape (3 saves, no ambiguous-attack-selection contexts), and legacy fidelity was assumed to be a hard requirement at every step, which made the 6-save/3-save mismatch and the finesse max(STR,DEX) formula look like real design gaps rather than mechanical work.

**Attempt 3 (2026-08-01, same day, after design lead relaxed the fidelity requirement):** both remaining blockers closed. **Key unlock: legacy-mode fidelity was declared non-required mid-migration** (legacy is disposable scaffolding, fully retired at M2 — see the plan's "Recommended execution order" 2026-08-01 update). Once byte-identical matching was no longer the bar, both "blockers" turned out to be mechanical after all — they only *looked* like design decisions because attempt 2 was holding itself to a fidelity standard nobody actually required.

**What shipped:**
- Saves: added two legacy-only `derivedStatMap` entries (`prowessSave`, `intellectSave` — STR-save/INT-save have no target-system meaning but legacy code still computes all 6) plus a new `RULES.attributes.legacySaveAbilityToContext` mapping table (legacy key -> save context; WIS and CHA both route to `composureSave`, the documented imperfect approximation). Wired `Character.initializeSavingThrows()`, `EffectDispatcher.maneuverSaveDC()`/`rollDefenderSave()`. `maneuverSaveDC`'s old `max(STR,DEX)` became Prowess-only (`meleeAttack` context) — the resolver has no max-blend primitive, and inventing one for a soon-to-be-replaced legacy formula would have been the "new abstraction" the hard boundaries forbid; dropping to one term was the correct call once fidelity was relaxed, not a `backend-dev` handoff.
- Attacks: melee/ranged/finesse resolution in `Character.getAttackBonus()`, `CombatManager`'s main `attack()` path, and `CombatManager.calculateMonsterAttackStats()` all wired to `rangedFinesseAttack`/`meleeAttack` contexts (both resolve to Prowess/STR in legacy mode — ranged and finesse lose their old DEX/max(STR,DEX) bonus). This is intentional per the plan (attack is deliberately single-stat Prowess even in the target design), not a legacy-only compromise.
- Found and removed 3 pieces of confirmed-dead code discovered while auditing this exact formula: `Character.getManeuverSaveDC()`, `CombatManager.getManeuverSaveDC(attacker)` (both zero call sites, duplicated the pre-fix `max(STR,DEX)` formula and would have silently drifted from the real fix in `EffectDispatcher.js`), and noted (not removed — different file area, not touched) `CombatManager.makeSavingThrow()` is also dead code (zero call sites) discovered during the saves audit.
- Judgment call, not literally in the named task list: `Player.js`/`EncounterBuilder.js`'s "duplicated modifier-calc sites" turned out to be plain 6-key `abilityModifiers` cache construction (`Math.floor((score-10)/2)` per key), not melee/ranged/finesse branching — there was no attack-ability-selection logic in either file. Wiring these through the attribute resolver would have been pure indirection for an identical value (a "derived stat context" redirect onto a flat unconditional legacy-key cache is not what the resolver is for) — exactly the kind of unnecessary abstraction the hard boundaries forbid. Fixed the *actual* duplication instead: both sites reimplemented the modifier formula inline instead of calling the existing shared `getAbilityModifier()` helper from `dice.js` (which `Character.calculateAbilityModifiers()` already used correctly) — collapsed to that call, zero behavior change, no resolver involved.
- Test fixture fix required in 3 files (`character.characterization.test.js` was already fine; `effectDispatcher.characterization.test.js` and `combatManager.characterization.test.js` needed it): their `makeCharacter()` helpers only set `.abilityModifiers` (pre-floored), never `.abilities` (raw scores) — the resolver reads only `.abilities`. Fixed by deriving `.abilities` from `.abilityModifiers` in the fixture (`score = mod*2+10`, exact inverse of the floor formula for integer mods), same fix shape as the initiative-test fix from attempt 2, now generalized at the fixture level instead of per-test. Explicit `overrides.abilities` (already used by 4 pre-existing initiative tests) still wins via merge order — no ripple to those.
- Test assertions updated for behavior that's no longer expected to hold (max(STR,DEX)/DEX-only ranged): 2 tests in `effectDispatcher.characterization.test.js`, 2 tests in `combatManager.characterization.test.js` renamed and re-asserted against the new Prowess-only formula. Net test count unchanged (345/345 before and after) — no tests added or deleted, only values/titles updated where the formula they were pinned to actually changed.

**Root lesson, updates [[feedback_verify_plumbing_before_wiring]]:** a "structural mismatch" blocker (6 legacy saves vs 3 new saves, or a missing max-blend primitive) is only a real design-call escalation if fidelity is actually required. Always check whether the fidelity requirement itself is still in force before escalating a shape mismatch — the same mismatch can be a hard blocker one day and a mechanical judgment call the next, purely because someone upstream changed the acceptance bar, not because the code changed.
