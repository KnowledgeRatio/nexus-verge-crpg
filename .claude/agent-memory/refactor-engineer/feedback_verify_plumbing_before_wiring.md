When a task hands off a "plumbing" module from an earlier milestone (e.g. a resolver/adapter another agent built and marked as zero-behavior-change or pass-through), verify that claim with a small live repro *before* starting the call-site swap, not after tests fail. In this project's attribute-system remap, `attributeResolver.js` documented itself as legacy-pass-through-safe but had no actual legacy/new-key translation — every call silently returned 0. A two-line Node repro (fake character object, call the exported function, compare to expected legacy value) caught this in seconds and avoided a mass edit that would have broken 341 tests and needed a full revert.

**Why:** This project's refactor tasks are staged explicitly so each step trusts the previous step's output as a stable contract (M0 plumbing → M1 wiring → M1.5 flip). A silent gap in that contract is invisible until wiring is attempted at scale, and reverting a multi-file sweep is much more expensive than a five-minute spike test up front.

**How to apply:** For any task that says "wire X call sites to already-built helper Y," write a throwaway script that calls Y with realistic input and diff the result against today's actual behavior before touching any real call site. If Y doesn't match, stop and escalate rather than patch Y — modifying a shared module another agent owns, outside your assigned scope, is a boundary call even when the fix looks mechanical. See [[project_attribute_remap_m1_blocked]].

**Generalization (2026-08-01, same task's retry):** the lesson isn't just "test the helper function," it's "test every individual mapping/config entry the helper consumes." The resolver itself was fixed and verified correct on retry, but a *second*, narrower version of the same gap showed up one layer up: `RULES.attributes.derivedStatMap` (a config table the resolver trusts) had entries shaped for the *target* system, not a faithful pass-through of legacy behavior, for exactly the contexts where legacy code branches on more than one input (attack ability selection by weapon type, which abilities have saves at all, max()-based DC formulas). Single-attribute no-branching contexts (DEX→AC, DEX→initiative) were fine. Before wiring any call site, check whether the context being replaced is a *simple* literal read or a *branching* one (if/else/max/ternary choosing between abilities) — branching ones are the ones worth spike-testing against real inputs first, every time, even when the plumbing itself already checked out once.

**Correction (2026-08-01, third attempt, same day): a "branching = escalate" reflex can itself be wrong once fidelity requirements change.** The two branching contexts flagged above (6-save/3-save mismatch, max(STR,DEX) attack/DC formula) were escalated to `architect` as design gaps in the second attempt — but on the third attempt, once the design lead explicitly declared legacy-mode fidelity non-required (disposable scaffolding, not a permanent contract), both turned out to be closeable with ordinary mechanical judgment: add legacy-only scaffolding contexts to `derivedStatMap` for the missing saves, and collapse ambiguous branches to their single dominant term. The "branching = spike-test and possibly escalate" rule from the paragraph above still holds — but *escalate* is conditional on fidelity actually being required. Always check whether the acceptance bar (byte-identical vs. "reasonable judgment, legacy is scaffolding") has changed before treating a structural mismatch as a hard blocker; the same mismatch is a design call under one bar and routine cleanup under the other. See [[project_attribute_remap_m1_complete]] for the specific resolution.
