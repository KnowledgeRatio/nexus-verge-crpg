Full audit requested by design lead after tonight's Exemplar pass (Resolve-spend mechanic, save-reroll reactions, tactic system) repeatedly hit "generic-looking JSON read by nothing" or "needed new code anyway." Findings below are what's confirmed in the code as of 2026-08-06, superseding parts of [[architect]] MEMORY.md's older "Ability Dispatch Scalability (2026-04-09)" entry (that entry's hard blocker — `executeOnHitManeuver()` switch block — is now RESOLVED; the function no longer exists, tactics dispatch cleanly through EffectDispatcher).

**Why:** This is the reference audit for any future "should we build a generic conditional-trigger/buff-debuff layer before Scholar/Wanderlust" conversation.
**How to apply:** Cite this before re-deriving any of these findings from scratch. Verify line numbers still hold (files churn) before quoting to game-designer/backend-dev.

## What's confirmed genuinely reusable (zero new code for a new ability)
- `EffectDispatcher.js` flat handler map (`handlers[effectType]`, registered via `registerHandler`) — new ability referencing an existing effect type (`heal`, `dodge`, `extraAction`, `cureCondition`, `variableCostHeal`, `variableCostDamage`, `onHitSaveOrCondition`, `onHitCondition`, `onHitPush`, `selfTempHP`, `allyTempHP`, `precisionAttackBonus`, `reactionAttack`, `reactionDamageReduction`, `rerollSavingThrow`) with new JSON params works with zero JS changes. Confirmed by direct read, `EffectDispatcher.js` full file.
- Resolve resource gate: `EffectDispatcher.js` execute(), lines 49-58. Single pre-dispatch gate keyed on `ability.resourceType === 'resolve'`. Any new ability tagged that way is correctly gated. No ability-specific code.
- `canUseAbility`/`getAbilityUsesText`/`trackAbilityUsage` (main.js ~3384, ~3431, ~3753) for `resourceType: 'shortRest'` — genuinely generic, keyed by `ability.id` as a dict key into `character.abilityUses`, `usesPerShortRest` read off the ability JSON.
- `addCondition(type, duration, appliedBy, options)` (CombatManager.js ~2834) — fully generic condition **storage**: arbitrary type string, arbitrary duration enum value (`'rounds'|'untilStartOfTurn'|'untilEndOfTurn'|'combat'|'permanent'`, tick/expiry logic at CombatManager.js ~269, ~301, ~3077 is keyed on the duration enum, not on condition type), arbitrary numeric `value`, stacking behavior. A new named condition applies and expires correctly with zero new code.
- `_isTacticAbility()` (main.js ~3467) — checks membership in a fixed array of effect-type strings, not ability IDs. Correct ADR-010 pattern for "is this ability part of category X."
- Equipment/item effect catalog: `getActiveEffect(target, category, property)` / `getActiveSlotEffect(attacker, slot, category, property)` (CombatManager.js, e.g. ~664, ~787, ~1090, ~1228) — a fourth, separate generic effect-lookup system for item-granted properties (`modifyDefense.critImmunity`, `modifyWeapon.critRange`, `modifyWeapon.damageBonus`, `modifyShield.savingThrowReaction`). Not itself in scope of this audit but worth knowing it exists as a fourth parallel "effects" mechanism alongside EffectDispatcher, PassiveModifierRegistry, and conditions.

## Confirmed ceilings / gaps (each is a specific missing primitive, not a vague "needs more code")

1. **Conditions are a generic storage primitive but NOT a generic effect primitive.** Every mechanical consequence of a named condition (`dodging` → attacker disadvantage, `sapped`/`prone`/`frightened`/`harried`/`pushed`/`disarmed` → various attack-roll modifiers) is a separate hardcoded `hasCondition('X')` check scattered across ~15+ call sites in `CombatManager.js` attack()/other resolution code (confirmed via grep, e.g. lines 590, 605, 613, 619, 631, 913, 942, 948, 954, 976, 988, 994, 1064, 1727, 2964). A brand-new condition name in JSON does literally nothing mechanically unless it happens to match one of these already-wired strings. **This directly generalizes to any future Scholar spell like Bane/Bless that grants advantage/disadvantage** — it would need new hardcoded checks at every relevant roll site, the same way `dodging` does today.

2. **No unified "roll a saving throw" function exists — three independent, inconsistent implementations.** (a) `rollDefenderSave()` in `EffectDispatcher.js` (~533-548) — supports override savingThrows, disadvantage. (b) inline calc in `CombatManager.executeSpecialMonsterAction()` (~780-806) — supports a `savingThrowReaction` shield-AC-add reaction, no override/disadvantage support. (c) inline calc for Topple weapon mastery (~1573-1589) — no override, no disadvantage, no reaction hook at all. Only path (b) has the new `afterFailedSave` reaction hook wired to it (main.js `promptReaction`, hookPoint `afterFailedSave`). **Concretely: Indomitable (reroll a failed save) will NOT trigger on a failed Topple save, and will not trigger on any future spell's saving throw unless that spell's resolver independently remembers to call `promptReaction('afterFailedSave', ...)`.** This is the real cost behind "a whole new reaction hookpoint" — it's not actually a system-wide hook, it's one call site. Building Scholar spells with saves will hit this immediately.

3. **No generic "pre-attack-roll conditional modifier" hookpoint keyed on battlefield/target state (as opposed to the attacker's own resource/condition).** Vanguard (`data/traits.json` id `vanguard`, `effects: []` — the trait's own JSON carries zero mechanical data) is implemented as ~50 lines hardcoded directly inline in `CombatManager.attack()` (~1070-1122), gated by `attacker.character?.selectedTraits?.includes('vanguard')`, computing a pre-mutation snapshot (`defender.engagedWith.size === 0`, read *before* the attack's own engagement-mutation block later in the same function) plus ad-hoc attack/damage bonus terms added into `attackTotal`. This is the single worst coupling point found tonight — trait-ID branching baked into the core attack() roll math, not dispatched anywhere. **Generalizes directly to any future "first attack vs. an unaware/unengaged/surprised target" mechanic** (Sneak Attack, Assassinate-style abilities are the obvious D&D analogues) — each would need the same kind of hand-rolled insertion into `attack()`.

4. **No generic "does the target have a condition my own tactic inflicted" cross-reference + one-shot-consumption primitive.** Grace Under Pressure (`data/traits.json` id `grace_under_pressure`, also `effects: []`) needed a bespoke helper `checkExposedDisadvantage()` (`EffectDispatcher.js` ~450-469) — reads `attacker.character.selectedTraits.includes('grace_under_pressure')` (a hardcoded trait-ID string check, structurally the same category of violation ADR-010 names for ability IDs, just one level removed — it's centralized in one function reused by three tactic handlers rather than duplicated, which is the one mitigating factor) and searches `defender.conditions` for one flagged `inflictedByTactic && appliedBy === attacker.id && !exposedConsumed`, then sets a one-shot `exposedConsumed` flag on that specific condition object. **The generalizable missing primitive: no data-driven way to say "grant [effect] the next time [trigger condition] is met, consumed once" — every such passive today requires a new named boolean flag on the condition object plus new code that checks and consumes it.**

5. **`data/traits.json`'s effect vocabulary (`attackBonus`, `acBonus`, `damageBonus`, `rerollDamage`, `reactionAbility`, `unarmedDamage`, `sense`, `movement`, `terrainTraversal`, `freeObjectInteraction` — confirmed present at lines 16, 44, 72, 102, 137, 167, 196, 206, 236, 262, 288, 319, 327, 336) is entirely decorative/dead.** Grepped the whole `src/` tree — nothing reads `trait.effects` for any of these types at runtime. The only consumer of `data/traits.json` is `main.js` `renderClassFeatures()` (~6320-6333), which reads `trait.name`/`trait.description` for display only, and `LevelUpManager.js` for the trait-selection UI (name/description/category filtering). **Every mechanical trait shipped so far (Vanguard, Grace Under Pressure, and by extension likely earlier ones) bypasses this vocabulary entirely and goes straight to hardcoded JS**, which is presumably *why* the vocabulary looks unused — the schema was designed once, aspirationally, and every actual implementation since has ignored it in favor of ad hoc code. This is the clearest instance of "a generic-looking JSON field turned out to be read by nothing" the design lead described.

6. **`character.abilityUses` reset logic is not actually keyed by `resourceType`, despite `canUseAbility` reading it as if it were.** `Character.shortRest()` (Character.js ~1011-1015) unconditionally does `this.abilityUses = {}` — this clears uses for ANY ability regardless of whether its `resourceType` is `shortRest` or `longRest`. `Character.longRest()` (Character.js ~1063-1101) never touches `abilityUses` at all. Net effect: a `longRest`-resourceType ability (none currently exist in `abilities.json` — grepped, only `resolve` ×10 and `shortRest` ×3 are in use) would have its uses wiped by a *short* rest and never restored by a long rest. This is a live trap for whoever authors the first `usesPerLongRest` ability — the JSON field will appear to work (the read side is correctly generic) but the reset side silently does the wrong thing.
7. **No generic per-battle ("once per combat") or per-turn ability-use primitive exists at all.** Only `shortRest`/`longRest`/`resolve` resourceTypes are handled anywhere in `canUseAbility`/`trackAbilityUsage`/`EffectDispatcher`'s gate. A "once per combat" ability (a very standard D&D pattern, e.g. many capstones) would need a new resourceType branch invented from scratch — confirmed via grep, no `perCombat`/`usesPerCombat`/`perTurn` handling exists anywhere in `src/`.

## Fighting styles — separate but related drift (found in passing, not part of the requested audit but same category)
`PassiveModifierRegistry.js` (created since the 2026-04-09 memory entry, which said it "must be built") now exists and IS a clean, generic ctx→value registry (`registerFightingStyle(styleId, hooks)`, hooks = `attackBonus`/`acBonus`/`damageBonus`/`unarmedDie`/`addsOffHandAbilityMod`/`shouldRerollDamage`, all pure functions of a context object). Confirmed callers: `main.js` ~8557, `Character.js` ~267, `CombatManager.js` ~935/~1218/~1228. BUT it is still pure hardcoded JS — no `data/fightingStyles.json` was ever created (the 2026-04-09 memory's deferred item #3 is half-done: the registry got built, the data file didn't). Worse, `main.js getFightingStyleDetails()` (~6350-6403) is a SECOND hardcoded JS object duplicating fighting-style names/descriptions for display, entirely independent of `PassiveModifierRegistry.js`'s numeric logic — two separate hardcoded sources of truth for the same eleven fighting styles, neither backed by JSON. Adding a twelfth fighting style requires editing both files by hand. Same stateless-ctx-function ceiling as originally documented: no conditional/multi-step logic, no one-shot consumption, no reading a target's condition list.

## Recommendation given to design lead (2026-08-06)
Incremental extension of the current EffectDispatcher/handler-table approach is sufficient for pure "apply a formula-based buff/heal/damage on a known trigger" content (that's what's already working well). It is NOT sufficient to reach "author most new content as JSON" for anything that needs (a) a conditional check against battlefield/target state before a roll, (b) a save-based spell whose failed-save reaction needs to fire correctly, or (c) a passive that reacts to another passive's tag. Recommended three concrete additions before Scholar/Wanderlust spell content starts, in priority order:
1. **Unify saving throws into one function** (`rollSavingThrow(defender, saveAbility, dc, options)`) that every save-resolution site calls, with the `afterFailedSave` reaction hook fired from inside that one function — closes finding #2, which is the most load-bearing (blocks Indomitable working reliably at all, blocks any future save-based spell).
2. **A generic pre-roll conditional-modifier list on the attack pipeline** — instead of ad hoc named local variables (`vanguardsChargeAttackBonus`, `maneuverAttackBonus`, `fatigueAttackMod`, ...) hardcoded into `attackTotal`'s sum, a list of `{ source, condition: ctx => bool, attackBonus, damageDice }` entries that `attack()` iterates generically. Closes finding #3 and gives Grace-Under-Pressure-style triggers (finding #4) a home without a bespoke helper per trait.
3. **A unified buff/debuff primitive that both the condition system and `traits.json`'s (currently dead) flat-modifier vocabulary route through** — so applying a named condition and having it produce a mechanical effect are the same declarative act, closing finding #1 and finally giving `traits.json`'s existing schema (finding #5) a real consumer instead of deleting it as dead code.
None of these were implemented — this is a scoping report only, per instruction.
