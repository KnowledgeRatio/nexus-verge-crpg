Oath (Dedication's second specialization) identity pass scoped 2026-08-06, mirroring Exemplar's prior identity work. Full file-by-file plan handed to backend-dev/data-agent/frontend-dev — not yet implemented as of this writing.

**Why:** Exemplar got Grace Under Pressure/Vanguard + tactic curation; Oath was left as a placeholder (auto-granted Sworn Strike/Aid the Vulnerable only). This pass adds 3 Auras (pick 1 at L3) and a 5-Vow pool (pick 3 of 5 across L5/7/9), parallel to Exemplar's tactic-pool shape.

**How to apply:** If asked about Oath, Dedication auras, or reaction-on-ally's-behalf work, this is the grounding pass — verify against code before reuse, per architect protocol, since implementation hadn't landed yet as of 2026-08-06.

## Verified against real code (2026-08-06)

- `data/specializations.json` **already has** a real `oath` entry (not `.example` only) — a prior memory note claiming this file was missing is stale, corrected.
- Monster "abilities: [] NaN bug (19/46 monsters)" **does not reproduce**. Checked directly: 0/46 monsters have array-type or missing `abilities`; all 46 have full stat-block objects. `EncounterBuilder.js`'s `createEnemyFromMonster()` already converts via `convertLegacyAbilitiesToSixAttribute()` (null-safe, returns `{}` on missing input) and `convertMonsterSavingThrows()` (also null-safe). This machinery was built 2026-08-01–03 as part of the attribute-system remap (ADR-015 fork) — almost certainly postdates whatever balance-engineer pass originally found the bug. Flagged back to the requester rather than silently working around it; if Challenge (Oath's new Vow) needs real empirical verification, that's a fresh balance-engineer pass against current code, not a known fix to re-apply.
- `docs/plans/2026-08-06-generic-ability-effect-schema.md` is **Proposed, Phase 1 not started** — no `EffectDispatcherV2.js`, `data/resources.json`, or `data/conditions.json` exist yet. Oath's new content must NOT depend on this; it uses the existing (legacy-shape) `EffectDispatcher.js` handler-registry pattern, same as every other live ability.
- `subtype` field on abilities.json entries **already exists and is populated** (`"ability"`, `"tactic"` seen in data) — a prior memory note calling this a schema gap is stale/resolved. New Oath content should use `"subtype": "vow"` for the 5 pool abilities (new value, following the same convention).
- `renderTacticChoice()`/`renderManeuverChoice()` in `LevelUpManager.js` (~line 562) still hardcodes `ab.specialization === 'exemplar'` rather than reading `subtype` — that specific memory item (schema gap for the picker) is still real, just distinct from the `subtype`-field-missing claim.

## Architectural gaps the brief did not fully name (found during scoping, not pre-flagged)

1. **No generic "targeted-save, no-attack-roll" ability dispatch shape exists.** Every existing enemy-targeting path is either on-hit (requires a prior weapon attack: tactics, Sworn Strike) or the `weapon_attack` deferred type (also requires an attack roll). Challenge (bonus action, target an enemy, straight save, no attack roll) needs a **new** deferred effect type (`targetedSaveOrCondition`), a new `main.js` `selectedAction` branch (`abilityTargetedSave`) parallel to the existing `abilityWeaponAttack` branch, and `checkDeferred()`'s caller needs to read *which* deferred type it got back (today it's a bare boolean) to route to the right `selectedAction`. This is real new engine work on top of the brief's two named blockers.
2. **`promptReaction()`'s three inline reaction-button handlers conflate "the defender" with "the reactor."** Not just the two lines the brief named (`defender.team !== 'player'` gate, `gameState.get('character')` hardcode) — the button click handlers themselves do `_buildCtx(character, defender, this.combatManager)`, i.e. they pass `defender` as `ctx.combatant`. For Reprisal/Intervene, the reactor (Oath) and the defender (ally being attacked) are different combatants; every one of those three branches needs a `reactor` parameter threaded through, not just the entry gate. Fix: add an explicit `reactor` param to `promptReaction(hookPoint, attacker, defender, ctx, reactor = defender)`, default preserves today's behavior for Riposte/Parry/Indomitable exactly.
3. **`character = gameState.get('character')` is fine to replace with `reactor.character`** — verified `Combatant.character` is stored by reference from whatever was passed into `startCombat()`, so for the player this is the same live object `gameState.get('character')` would return; for a companion it's the companion's own object. Note: `EffectDispatcher.execute()`'s Resolve-gate (lines 49–58) unconditionally does `gameState.set('character', context.character)` — this is a **pre-existing bug** if a companion ever uses any Resolve-cost ability (would overwrite the player's gameState slot with companion data). Not introduced by Oath, not fixed by this pass — flagged, scoped as "reactor is always the player character for this pass" (companions aren't interactively prompted for reactions yet; no UI exists for it), but the underlying gameState.set bug should be on record for whenever party-system combat wiring picks this up.
4. **Saving throws are implemented in three separate places**, confirmed still true: `EffectDispatcher.rollDefenderSave()` (goes through `getAttributeModifierFor`/`derivedStatMap`, NVSystem-aware), `CombatManager.executeSpecialMonsterAction()` (own inline DC-parse-from-description + raw `abilityModifiers[key]` lookup, bypasses the attribute resolver entirely), and Topple mastery's inline CON save (same bypass). Aura of Mercy (+1 ally saves) needs a call added at all three sites — there is no single choke point. Scoped as one new shared helper (`getAuraSaveBonus(combatManager, defenderCombatant)`), called additively from each of the three sites — not a refactor of the three into one.
5. **`PassiveModifierRegistry.js` only answers "what does MY OWN `styleId` give me"** — a single-character self-lookup keyed by one value per character. Auras are structurally different: a cross-character query ("scan all allied combatants in this fight for an active aura trait, check engagement overlap with the recipient, sum"). Concluded this needs a **new function set**, not an extension of `registerFightingStyle()`'s shape — proposed living in the same file (additive export) rather than a new system, since it's small and conceptually adjacent.
6. **AC comparison and damage-total composition are both single clean insertion points** in `CombatManager.attack()`: `const effectiveAC = defender.ac + coverACBonus;` (line ~1086) for Aura of Sanctuary, and `const damageTotal = damageRoll + damageBonus + forgecraftDamageBonus + extraDamage;` (line ~1234) for Aura of Wrath. Both are single-term-addition edits, low risk.
7. **Slow weapon mastery (`CombatManager.js` ~1553–1571) is the exact working precedent** for "condition + direct `.ac -= 1` mutation, `untilStartOfTurn` duration" — used as the template for Challenge's "-1 AC to an attacker who hits the Taunt source anyway" clause, and confirms `appliedBy` on an `untilStartOfTurn` condition is who it clears *for* (their next turn), which is why Taunted's `appliedBy` must be the Oath's combatant id (clears at the Oath's next turn), not the taunted enemy's.
8. **Reaction abilities are only hidden from the manual ability-list modal if they're tactic-typed** (`main.js` ~3287: `ability.actionType === 'reaction' && this._isTacticAbility(ability)`). Indomitable (a non-tactic reaction) is not excluded by this filter today — likely a pre-existing minor gap, not previously flagged. Reprisal/Intervene would inherit the same gap unless the filter is generalized to hide *all* `actionType === 'reaction'` abilities from manual use, since reactions only make sense via `promptReaction`'s trigger context. Recommended as a small bundled fix alongside the new `knownVows` filter, not a separate workstream.
9. **No characterization tests exist yet for Sworn Strike, Aid the Vulnerable, Steady Nerve, or Action Surge** (confirmed via the 2026-08-06 schema-fork plan's own audit, still true) — Oath's new Vow pool adds more surface to the same live `EffectDispatcher`/`CombatManager` on-hit and reaction paths. Worth closing this gap before or alongside the Oath work, not after.

## Reusable pattern census (confirmed still live, safe to build on)

- `specializationFeatures.{spec}.autoGrantTraits` / `autoGrantAbilities` in `levelProgression.json`, processed generically in `LevelUpManager.confirmLevelUp()` (~line 772-810) — works for any calling/spec, zero code change needed to add Oath's L3 aura auto-grant-into-choice (though auras are *picked*, not auto-granted, so this needs the pool-choice pattern below, not the auto-grant one).
- Tactic-pool pattern (`choice.type: "tactic"`, `character.knownTactics[]`, `renderTacticChoice()`, tag-based filtering via `tags: ["tactic"]`) is the direct template for a parallel `choice.type: "vow"` / `character.knownVows[]` / `renderVowChoice()` / `tags: ["vow"]`. Deliberately mirrored rather than generalized into one config-driven "pool chooser" — matches the existing convention of `specialization` and `tactic` already being two separate hardcoded choice types, not one; flagged as acceptable, bounded duplication, not a violation.
- `character._getKnownAbilityDefinitions()` (Character.js ~997) and `CombatManager._findKnownAbility()` (~2544) both union `selectedAbilities` + `knownTactics` — both need `knownVows` added to that union once it exists, or Vow abilities silently won't resolve their own definitions (same bug class as the pre-remap `knownTactics`-omission bug documented in `docs/callings/dedication.md`'s Known Implementation Gaps).
- Zealous Smite's kill-check hook point is real and precise: `CombatManager.attack()`'s variable-cost-damage branch (~line 1332-1345), specifically the `if (resolveSpent > 0 && defender.hp > 0)` block after `dispatchAbilityEffects(onHitDamageAbility, ...)` resolves — this is the only place Sworn Strike's damage is applied and defeat is checked in the same call stack. The "kill-trigger pattern considered and shelved earlier tonight" referenced in the brief could not be located in `docs/plans/` or elsewhere in the repo — treated as informal/undocumented, not reused as a named artifact; scoped Zealous Smite against the actual code path instead.
