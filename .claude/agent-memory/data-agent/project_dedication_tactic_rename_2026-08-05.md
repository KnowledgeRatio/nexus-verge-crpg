Implemented the Dedication calling data layer: renamed `abilities.json`'s maneuver `subtype`/`maneuverDie` value strings to `tactic`/`tacticDie` across all 8 tactic entries, fixed Menacing Attack's `saveType` (`wis` -> `composure`), converted Rally to a `{choice, options}` shape with a new `allyTempHP` option, added three new abilities (`indomitable`, `exposed`, `vanguardsCharge`), and updated `levelProgression.json`'s dedication block (L2 Indomitable, L3 tactic rename + Exposed auto-grant, L4/6/8 optional practice choices, L5 Vanguard's Charge auto-grant, L7/9 optional tactic choices). Also added the Pushing Attack ADR-014 substitution row to `.claude/rules/architecture.md`.

**The upstream brief's "confirmed-dead field" claim was half wrong — verify per-field, not per-name-collision.** The brief asserted both `ability.subtype` and the string value `"maneuverDie"` were dead in code, and by implication that renaming `levelProgression.json`'s `choices[].type: "maneuver"` was equally safe. `ability.subtype` and the `"maneuverDie"` dice-value strings genuinely are dead (grepped `src/` — `EffectDispatcher.js` only mentions `"maneuverDie"` in JSDoc comments, the handlers always call `rollManeuverDie()` regardless of the config value). But `levelProgression.json`'s `choices[].type === 'maneuver'` is very much alive: `LevelUpManager.js` has a literal `case 'maneuver':` in `renderChoiceSections`'s switch, plus two more `c.type === 'maneuver'` equality checks (spec-selection show/hide logic, required-choice validation). Renaming that field to `'tactic'` in data with no matching code change means the level-3 (and new L7/L9) tactic-selection UI silently never renders — flagged hard for `backend-dev` rather than silently trusting the brief. General lesson: "field X is dead" checked in one file doesn't transfer to a same-named-but-different field in a sibling file just because a design brief bundles them together — grep each field independently.

**Extra Attack lives in `callingProgression.json`, not `levelProgression.json`.** The brief instructed "don't touch the existing Extra Attack `newFeatures` entry at level 5" in `levelProgression.json` — no such entry exists there; `levelProgression.json` level 5 had empty `choices` and no `newFeatures` at all. The actual Extra Attack grant is in `data/callingProgression.json` under `progressionRules.dedication.automaticGrants.5` (a completely separate auto-grant file/schema, keyed by `type`/`id`/`source`/`description`, not `newFeatures`). Two different level-progression data files coexist for dedication: `levelProgression.json` (player-facing choices/newFeatures/specializationFeatures, read by `LevelUpManager.js`) and `callingProgression.json` (automatic grants/choices, different consumer). Check both before assuming a level's content is exhaustively described by one file.
