**What happened:** M2 of `docs/plans/2026-07-30-attribute-system-remap.md` — added native `*SixAttribute` sibling fields (dual-field convention, same shape as [[project_kits_json_dual_shape_convention]]) to `monsters.json` (`abilitiesSixAttribute`, `savingThrowsSixAttribute`), `races.json` (`abilityScoreIncreaseSixAttribute`), `classes.json` (`primaryAbilitySixAttribute`, `savingThrowProficienciesSixAttribute`), `backgrounds.json` (`abilityScoreIncreasesSixAttribute`). Bijection used throughout: str→prowess, con→vitality, int→intellect, dex→insight, wis→composure, cha→presence (matches `RULES.attributes.legacyToNew` in `rulesEngine.js` exactly — verify against that constant before reusing this mapping, don't hand-derive it again).

**Tooling lesson — never rewrite a whole JSON file through a full parse+`json.dump`/`JSON.stringify` round-trip to make a small addition.** First attempt did `json.load` → mutate → `json.dump(indent=2)` on `monsters.json` and produced a 750-insertion/146-deletion diff for what should have been a ~220-line additive change — Python's `json.dump` escaped em-dashes to `—` and collapsed single-line arrays (`["blood"]`) into multi-line, touching every entry in the file, not just the ones being edited. Caught via `git diff --stat` before it could ship. Fix: use regex to locate the exact existing block as text and splice the new sibling field in as a string insertion, or use the `Edit` tool's exact-string-match per entry — never round-trip the whole file through a JSON serializer just to add a few keys. Re-verify with `git diff --stat` after any data-file edit that a full-file rewrite wasn't accidentally triggered — the diff stat is the tripwire.

**Real bug found, not caused by this migration: 19 of 46 monsters in `monsters.json` have `"abilities": []` (empty array) instead of a real `{str,dex,con,int,wis,cha}` block** — shadow, ghoul, specter, ghast, gargoyle, minotaur, wight, owlbear, flameskull, ettin, troll, wraith, hillGiant, the 3 dragons, manticore, mage, medusa. Confirmed via `git log -p --follow` present since the initial public-release commit (`4499f8a`) — not a regression, a longstanding gap. These monsters have **no functioning ability scores in legacy mode either**, so it's a standalone content bug, not something the six-attribute migration created or is blocked by. Handled by converting only the 27 monsters with real data and leaving the 19 broken ones untouched (fabricating CR-appropriate stat blocks is a `game-designer`/`balance-engineer` call, not a mechanical bijection — out of `data-agent` scope). **Flag this for `game-designer`/`backend-dev` independently of the attribute migration** — it's a pre-existing, live gap affecting monster viability in the current legacy system too, worth its own fix regardless of six-attribute progress. A monster's `savingThrows` field is independent of its `abilities` field (zombie/mage's saves converted fine even though mage's `abilities` is broken) — don't assume one broken field means the whole entry is unusable.

**Stale plan claim caught and corrected in the plan doc itself:** the plan's "Open ambiguous cases" table claimed Acolyte/Sage's `abilityScoreIncreases: ["int","wis","cha"]` collapses to a duplicate Composure entry under the new bijection. That claim predates a *later* section in the same document ("Legacy split-attribute conversion — DECIDED 2026-07-31") that locked `cha`→Presence, not `cha`→Composure. Under the actual shipped `RULES.attributes.legacyToNew`, `wis` and `cha` land on different targets (composure, presence) — no collision, converts cleanly to `["intellect","composure","presence"]`. Corrected in the plan doc per the workflow "update on contact" rule rather than silently working around it. **Lesson: a plan can go stale against its own later sections, not just against the code** — when a plan's early "open question" table cites a mapping, re-check it against that same plan's final locked decision before trusting it, especially in a long iteratively-edited design doc.

**Judgment call flagged, not resolved: `classes.json`'s Scholar/Wanderlust `savingThrowProficiencies`.** Dedication converts cleanly to the locked single-proficiency `["vitality"]`. Scholar (`["int","wis"]`) and Wanderlust (`["dex","int"]`) both include `int`, which has no valid save target under the locked pure-Inward-only save model (Intellect-save is retired, not just deprioritized) — no sixAttribute value was invented for either. `primaryAbilitySixAttribute` was still added for both (straight bijection, no such conflict — Scholar→`["intellect"]`, Wanderlust→`["insight","presence"]`) since primary-ability lists don't hit the same invalid-save-target problem. This mirrors the plan's own "not locked" forward note about Scholar/Wanderlust save proficiency — don't invent a value where the plan itself says the design isn't decided yet.

**Also spotted, out of scope for this pass, worth a separate flag:** `races.json`'s `dragonborn.dragonAncestry.damageTypes` map still uses fully deprecated damage types (`acid`, `lightning`, `fire`, `poison`, `cold`) — none of the locked 6-type taxonomy ([[project_damage_type_taxonomy]]). That migration's "zero deprecated values remain, verified by grep" claim apparently didn't catch this field (different key shape — `damageTypes` map, not a singular `damageType` string — may have evaded whatever grep pattern was used). Not fixed here (out of this session's requested scope), flagged for whoever picks up the damage-type migration follow-up.
