Six-attribute remap (`docs/plans/2026-07-30-attribute-system-remap.md`) M1 step 6 landed 2026-08-01: the three blended target-system formulas (concentration, flee, Menacing Attack DC), the monster-loader saves shim, and the Trip/Pushing/Disarming Attack `saveType` data flip. `RULES.attributes.system` default is still `'legacy'` — nothing below is live until the M1.5 flag flip. 370/370 tests passing after this step (up from 345).

**Why:** design lead locked these three formulas' math in the plan; this was the step that actually wired them into the resolver/derivedStatMap and gated the real call sites (`CombatManager.flee()`, `EffectDispatcher.maneuverSaveDC()`) on `RULES.attributes.system === 'sixAttribute'`, leaving legacy-mode behavior alone per the relaxed-fidelity rule set at M1 step 5.

**How to apply / key implementation facts for later remap work:**
- Concentration has zero live callers — the deliverable was just the formula being correct and tested via `getBlendedAttributeModifier(character, 'concentration')` directly (no wrapper function added; would have been speculative dead code). Don't invent a concentration mechanic when touching this again.
- `CombatManager.flee()` now branches on `RULES.attributes.system`: sixAttribute uses `getBlendedAttributeModifier(combatant.character, 'flee')`, legacy keeps the original `max(dexMod, wisMod)` inline. The flee-check message's stat label (`'Prowess+Insight blend'` vs `'max DEX/WIS'`) is also branched — don't forget the label if touching this again, a test pins the exact string.
- `EffectDispatcher.maneuverSaveDC(character, config)` gained a second param. Default formula unchanged (Prowess-only via `getAttributeModifierFor(character, 'meleeAttack')`). `config?.dcContext` + sixAttribute mode overrides to `getBlendedAttributeModifier(character, config.dcContext)`. All three on-hit handlers (`onHitSaveOrCondition`, `onHitCondition`, `onHitPush`) now pass `config` through. `data/abilities.json`'s `menacingAttack` has `dcContext: "menacingAttackDC"` on its `onHitSaveOrCondition` effect; Trip/Pushing/Disarming Attack have no `dcContext` and stay on the shared default in both modes — this is the ADR-010-compliant way this was done (generic field read, no `ability.id` branching).
- **Non-obvious fix, matters for any future `saveType` value:** `EffectDispatcher.rollDefenderSave()`'s context lookup was `RULES.attributes.legacySaveAbilityToContext[saveAbility]` with no fallback — that map only has the six legacy abbreviations as keys. Trip/Pushing/Disarming Attack's `saveType` flipped from `"str"` to `"vitality"` (decision #5, both legacy AND sixAttribute mode — this is a real behavior change even in legacy mode, defender now saves off CON instead of STR, accepted under the relaxed-fidelity rule). `"vitality"` isn't a legacy key, so without a fix it silently resolved to `undefined` context → 0 modifier in **both** modes. Fixed generically: `RULES.attributes.legacySaveAbilityToContext[saveAbility] ?? \`${saveAbility}Save\`` — any new-system attribute name now falls through to derivedStatMap's `${attr}Save` naming convention. Apply the same fallback pattern if any other `saveType` field ever gets set to a new-system name directly.
- `onHitPush`'s messages used to hardcode the literal string `"STR save"` regardless of `config.saveType` (the only one of the three on-hit handlers that didn't build the label from `config.saveType`). Fixed to `${saveType.toUpperCase()} save` to match the other two handlers — otherwise it would have kept saying "STR save" after the data flip to `"vitality"`.
- Monster `savingThrows` (data/monsters.json's `{wis, cha, ...}` bonus-override block) has **zero live runtime consumer today** — nothing reads it during combat, confirmed by grep. The "monster-loader shim" is therefore just correctly attaching a converted `savingThrows` onto the enemy object at construction time for future-proofing, not fixing an active bug. New shared module: `src/utils/monsterAttributeConversion.js` (`averageComposureSaveBonus`, `convertMonsterSavingThrows` — con→vitality, dex→insight, wis+cha averaged→composure per decision #2, str/int dropped entirely per the Inward-only saves decision). Wired into `EncounterBuilder.js`'s `createEnemyFromMonster`, gated on sixAttribute mode via a conditional spread (legacy mode still attaches no `savingThrows` key at all — zero behavior change). **This must stay the one shared implementation** — the plan explicitly warns the future data-agent batch-convert script (46 monsters) must call this same function, not reimplement the averaging.
- Real data check before writing the shim: neither zombie nor mage (the two real monsters flagged as needing this) actually has both `wis` and `cha` present — each only has `wis`. The averaging function still had to handle the both-present case correctly (verified against the two non-canon dragon blocks' shape) since it's shared with the future 46-monster batch job, which will hit real both-present cases.
- Test files added this step: `tests/utils/attributeResolver.test.js` (new sixAttribute-mode blend describe block for all three formulas), `tests/systems/effectDispatcher.sixAttribute.test.js` (new file — Menacing Attack DC blend + Trip Attack's vitality saveType in both modes; kept separate from `effectDispatcher.characterization.test.js` because that file's docstring explicitly pins it to legacy-only behavior), `tests/systems/combatManager.characterization.test.js` (appended a sixAttribute-mode flee describe block — same file, since flee's legacy-mode block was already there and the pattern of flipping `RULES.attributes.system` in `beforeEach`/restoring in `afterEach` fit naturally), `tests/utils/monsterAttributeConversion.test.js` (new file, pure unit tests on the shared averaging function).

**Correction, 2026-08-01 (M1.5 flip-readiness bugfix pass):** the "370/370 passing" claim above was true but masked three real bugs, all found independently by `balance-engineer` (Monte Carlo) and `devils-advocate` against the actual implemented code, not just the tests — the existing test suite used fixtures that couldn't have caught any of them. All three fixed same day:
1. **`getBlendedAttributeModifier` never divided by attribute count.** It summed raw modifiers and floored once, but the locked formulas (decisions #3/#4/#5) are all `floor((A+B)/2)`, not `floor(A+B)`. Fixed to `Math.floor(total / entry.attributes.length)` (not a hardcoded `/2`, so it generalizes to any future blend width). This silently doubled every blended modifier in the game (concentration, flee, menacingAttackDC) versus the design lead's locked math. All expected values in `tests/utils/attributeResolver.test.js`, `tests/systems/effectDispatcher.sixAttribute.test.js`, and `tests/systems/combatManager.characterization.test.js`'s sixAttribute-mode blocks had to be recomputed — some worked-example pairs (e.g. Prowess+1.5/Presence+0.5) coincidentally landed on the *same* numeric answer under both the old buggy formula and the new correct one, which is a trap if you're eyeballing instead of recomputing by hand; I switched those specific fixtures to non-colliding values (Prowess+2.5/Presence+1.5, etc.) specifically so the tests keep discriminating bugged-vs-correct math.
2. **Game-breaking: nothing populated six-attribute-keyed `character.abilities`.** `attributeResolver.js`'s `resolveAbilityKey()` only redirects new-key->legacy-key in `'legacy'` mode; in `'sixAttribute'` mode it's a pass-through expecting `character.abilities.prowess` etc. to already exist. Neither `Character.js`'s `calculateAbilities()` nor `EncounterBuilder.js`'s `createEnemyFromMonster()` ever wrote those keys — every resolver call for every real character/monster silently returned 0 the instant the flag flipped on, regardless of real scores. Fixed with a new shared module, `src/utils/attributeConversion.js` (`convertLegacyAbilitiesToSixAttribute` — straight base-score copy via `RULES.attributes.legacyToNew`, not an average; don't confuse with `monsterAttributeConversion.js`'s wis+cha save-*averaging*, a different and narrower thing), called from both `Character.calculateAbilities()` (merges new keys onto the post-species-bonus, capped `abilities` object) and `EncounterBuilder.createEnemyFromMonster()` (merges onto `monster.abilities` before spreading into the enemy object), both gated on `RULES.attributes.system === 'sixAttribute'`.
   - **Why this specific bug survived 370 passing tests:** every existing sixAttribute-mode test (`attributeResolver.test.js`, `effectDispatcher.sixAttribute.test.js`, the flee block in `combatManager.characterization.test.js`) used hand-built fixtures with new-attribute keys already pre-populated (`{ abilities: { prowess: 13, presence: 11 } }`), never a real `new Character(...)` construction. That's a real blind spot pattern worth remembering for any future flag-gated migration: a resolver/redirect layer being *tested* isn't the same as the thing that's supposed to *populate* its inputs being tested. Added a new describe block to `tests/systems/character.characterization.test.js` (`Character abilities — sixAttribute mode (Bug 2 regression)`) that builds through the real `makeCharacter()` helper specifically to close this gap — future attribute-system test additions should default to real construction over hand-built fixtures unless there's a specific reason to isolate the resolver alone.
3. **`EffectDispatcher.rollDefenderSave()` never consulted the save-averaging shim's output.** `convertMonsterSavingThrows` (decision #2, `monsterAttributeConversion.js`) attaches an averaged Composure-save override onto `enemy.savingThrows` at construction time (zombie/mage — hand-authored wis/cha bonuses that don't perfectly match the ability modifier), but `rollDefenderSave()` only ever read the ability-modifier-derived default. Fixed with an "explicit override beats derived default" pattern: look up `RULES.attributes.derivedStatMap[contextKey].attributes[0]` (the attribute name, e.g. `'composure'`, NOT the `XSave` context key — the shim's output is keyed by bare attribute name) on `defender.character.savingThrows`, use it if it's a `typeof === 'number'`, else fall through to `getAttributeModifierFor()`. The `typeof === 'number'` check is doing real work, not just defensive boilerplate: a *player* character's own `character.savingThrows` (from `Character.initializeSavingThrows()`) is a totally different shape — keyed by legacy ability abbreviations (`str`/`dex`/...), each value an `{proficient, bonus}` object, not a bare number — so the same field name on two different object shapes never collides or false-positives, no mode check needed to keep them apart.

All three fixes plus 11 new regression tests (character construction path, the shared conversion function's own unit tests, and the override-vs-default save test) landed same day; 381/381 passing (up from 370). `RULES.attributes.system` default is unchanged, still `'legacy'` — none of this is live until M1.5's flip.
