Fixed 2026-08-01 in `src/systems/CombatManager.js`, found by a balance-engineer validation pass (`docs/plans/2026-07-30-attribute-system-remap.md`, though both bugs are orthogonal to that remap).

**Bug 1 — every equipped weapon silently dealt 1d4 fallback damage.** `attack()` read `weapon?.damage?.dice` / `weapon?.damage?.type`, but every weapon in `data/items.json` stores `damage` as a plain dice-notation string (`"damage": "1d12"`) with `damageType` as a sibling field, not `damage.dice`/`damage.type`. Since `weapon` was truthy, neither the object-read nor the `!weapon` unarmed-fallback branch matched — `damageDice` silently stayed at its initial value of `4`. Six call sites had the same bug (main hit, Parry reaction context, applyDamage, Cleave, Nick off-hand, Graze). Fixed via two module-level helpers, `getWeaponDamageDiceString(weapon)` / `getWeaponDamageType(weapon)`, that check `typeof weapon.damage === 'string'` first and fall back to `.dice`/`.type` only if it's ever an object (defensive, in case that shape reappears — see [[monsters_data_schema]] for where object-shape damage legitimately exists). `src/main.js:6733` already had this exact `item.damage.dice || item.damage` fallback pattern for inventory display — CombatManager just never got the same treatment.

**Bug 2 — crash on the 5 void-family monsters.** `calculateMonsterAttackStats()`'s non-weaponId branch called `.match()` directly on `action.damage`, assuming a string. The void monsters (`voidTrace`, `voidSpawn`, `voidHunter`, `voidShaper`, `voidTitan` — 7 actions total incl. Void Touch/Claw/Strike/Slam/Pulse/Entropy Pulse) use `action.damage = { dice, bonus?, type }` instead. Fixed by branching on `typeof action.damage === 'object'`. Design call made on the `bonus` field: when present, it replaces the damage-bonus contribution (SRD stat-block convention — the flat number already bakes in the monster's real modifier) but must NOT also overwrite `attackBonus` (the to-hit roll), since that's a separate concern — a first-draft fix accidentally reused the same `abilityMod` variable for both and would have corrupted to-hit. Needed a separate `damageBonusOverride` variable.

**Blind spot that let Bug 1 ship:** the existing characterization test fixtures in `tests/systems/combatManager.characterization.test.js` build weapon objects with `damage: { dice: '1d8' }` — the WRONG shape — because they were hand-written to "look like" what the code expected, not copied from real `items.json`. They only assert on the attack-roll message (not damage), so they never exercised the bug. New regression tests (`tests/systems/combatManager.weaponDamageRegression.test.js`) load `data/items.json`/`data/monsters.json` directly via `fs.readFileSync` instead of hand-built fixtures, specifically to avoid this recurring.

**Also found, not fixed (judged not low-risk/quick):** `Character.initializeSavingThrows()` always iterates the 6 legacy ability keys and sets `proficient` from `class.savingThrowProficiencies` (legacy list) regardless of `RULES.attributes.system`. In sixAttribute mode this shows e.g. a Dedication character proficient in both STR-save and CON-save instead of just CON (Vitality), per the plan's locked one-save-per-calling design (`data/classes.json` already carries a `savingThrowProficienciesSixAttribute` field per class that goes unused). Zero live impact today since `RULES.attributes.system` defaults to `'legacy'` and Prowess-save is never actually rolled. Not fixed because `src/main.js:6064-6069` renders saving throws by hardcoded legacy ability key (STR/DEX/CON/INT/WIS/CHA) regardless of system — a real fix requires deciding a legacy-key display mapping policy for the 3-save sixAttribute model (e.g. does Composure display under WIS or CHA, given both currently map to `composureSave`), which is a design call, not a pure bug fix. Flagged for game-designer/mechanics-master.
