Follow-up to [[attribute_remap_m1_formulas]] and [[attribute_remap_m2_readiness_sweep]]. This was the explicit M1→M2 gate check requested by the design lead: build real objects through real code paths (not hand-built fixtures) in `sixAttribute` mode and verify internal consistency end-to-end, specifically because the prior two passes' bugs (double-floor formula, unpopulated six-attribute abilities) both slipped past 370-then-411 passing tests by using fixtures that pre-populated exactly the keys the bug was in.

**Result: zero new bugs found. System is genuinely end-to-end functional for what M1 actually built** (chargen → `Character`, all three monster-spawn paths, live `CombatManager.attack()`/`flee()`, `EffectDispatcher` blended-DC saves). `RULES.attributes.system` is still `'legacy'` by default — nothing here is live until M1.5's flip. No source files were touched this pass (verification only); 417/417 existing tests still pass, confirmed unchanged.

**Method (reusable for future gate checks on this system):** standalone node script (not vitest) at scratch scope, not committed — stub `global.window/document/Audio`, override `global.fetch` to read real files off disk from `data/*.json` (strips cache-bust query strings), then: (1) instantiate the real `CharacterCreationUI`, call its real `loadData()`/`applyKitPreset()` against real `races.json`/`kits.json`/`classes.json`, construct a real `new Character(...)` exactly as `createCharacter()` does; (2) call the real exported `EncounterBuilder.buildEncounter()` with `monsterPool: [oneMonsterId]` and an XP budget sized to guarantee that exact monster is selected (`createEnemyFromMonster` itself is module-private, not exported — this is the only way to exercise it through a real public entry point without editing source); (3) construct real `Combatant` instances and call the real `CombatManager.attack()`/`flee()` directly (bypassing `startCombat()`'s DOM/window-dependent cover logic, which is already try/catch-guarded); (4) call the real `Player.js` `generateDungeonEnemy()` via `Object.create(Player.prototype)` (avoids constructing a full `Player` which needs a live game context).

**Specific things confirmed correct, real-construction, not fixture-based:**
- Chargen: Dwarf (con+2/wis+1, a discriminating racial bonus) + Dedication + Knight kit preset → `baseAbilities` stays legacy-keyed after `applyKitPreset()`'s bijection round-trip; `character.abilities`/`abilityModifiers` carry both legacy AND six-attribute keys; HP = hitDie + Vitality mod; AC = armor base + capped Insight mod; Athletics (Prowess) and Perception (Insight, **not** legacy WIS — the discriminating case, since Perception's legacy `ability` is `wis` but its `attributeSixAttribute` is `insight`, fed by DEX not WIS) both compute correctly and provably not via legacy passthrough (asserted `wisMod !== insightMod` on this specific build to rule out coincidental pass).
- Monster construction (goblin CR0.25, ogre CR2, mage CR6, via real `buildEncounter()`): every legacy ability key mirrors onto its bijective six-attribute key with correct modifiers, legacy keys stay populated (not clobbered), `abilityModifiers` populated generically for both key sets. Mage's `savingThrows` shim correctly produces `{ composure: 4 }` (wis:4 alone, no cha — first real monster construction test of the wis+cha averaging shim producing output that a later `rollDefenderSave()` unit test already covers on the consumption side) and correctly omits an `intellect` key (int-save retired).
- Live combat: chargen character (bumped to L3, given `selectedAbilities: ['menacingAttack']` for test purposes — this specific step is manual scaffolding, not exercising the real level-up flow) vs. real ogre, 6 real `CombatManager.attack()` rounds — no throws, real hits landed, Menacing Attack's blended DC (Prowess+Presence) computed sane and finite, Frightened condition applied via the real save path at least once across 20 repeated runs. `flee()` also exercised live (triggered a real opportunity attack from the ogre, then a real `combat.ended` emission) — no throws, no NaN.
- `Player.js generateDungeonEnemy()` (the third, previously-buggy monster-spawn path, [[attribute_remap_m2_readiness_sweep]]'s "Bug 2 fix hadn't reached this file yet" finding): now produces the same correctly-populated shape as the other two paths, and a real `CombatManager.attack()` against it (a different enemy-object shape than `EncounterBuilder`'s, since it omits `monsterActions`/`multiattack`) also completed without throwing.
- Ran the full 4-part script 20x back-to-back (RNG-dependent checks — "at least one hit lands," frightened triggers) with 0 failures on every run, not just once.

**Real findings, all pre-existing debt, none broken by the remap, none fixed (out of scope — not actually broken):**
- `Character.js` hardcodes `this.abilityModifiers.con` directly (not via the resolver) in `calculateMaxHP()`, `takeHitDie`/short-rest healing, `calculateMaxResolve()`, and `RestManager.js`'s long-rest healing; `CombatManager.js`'s Topple mastery save (line ~1509) does the same for its CON-save check. All four are numerically correct in `sixAttribute` mode today ONLY because CON→Vitality is a clean unsplit 1:1 bijection with no racial-bonus divergence possible — this is a landmine, not a live bug, if the attribute model ever stops being a pure bijection for CON. Also independently, Topple's save never adds the defender's save-proficiency bonus (reads raw ability modifier only) — a pre-existing simplification predating the remap entirely, unrelated to it, unaffected either way.
- `Character.initializeSavingThrows()` is still `const abilities = ['str','dex','con','int','wis','cha']` (all 6 legacy keys, unconditionally, in both modes) — the plan's own Architecture section (line ~312) states this should shrink to 3 keys (Vitality/Insight/Composure only) as part of the sixAttribute-mode implementation. It hasn't been done; `prowessSave`/`intellectSave` scaffolding entries in `derivedStatMap` exist specifically so this still works without crashing (rulesEngine.js's own comment calls them "legacy-mode-only scaffolding, delete at M2 shim retirement" — but they're actually still load-bearing in sixAttribute mode too today, not just legacy). Not broken (produces 6 duplicated-but-correct legacy-keyed entries), just an incomplete piece of the M1 architecture goal, deferred rather than done. Flag for whoever does the M2 shim retirement pass — that pass can't just delete `prowessSave`/`intellectSave` without also actually shrinking `initializeSavingThrows()` first, or `character.savingThrows.str`/`.int` will start resolving to `undefined` context.
- `Character.js`'s `updateSkillBonuses()`'s hand-maintained `skillAbilities` mirror (flagged as architecture debt in [[attribute_remap_m2_readiness_sweep]]) is currently byte-for-byte in sync with all 13 core skills' `attributeSixAttribute` field in `data/skills.json` — verified by direct comparison, not just by construction. Still fragile (no automated sync check), but not currently wrong.
- Unrelated to the remap entirely, found only because chargen was run for real: Dedication's starting equipment (`classes.json`'s `startingEquipment.defaults`, includes `"bolt:20"`) fails to resolve against `items.json` — `Item not found: bolt` (also `arrow`, `quiver`, likely a pre-existing ammo-item-id mismatch). Confirmed this is not new/not remap-caused; same failure would occur in legacy mode too. Not fixed (scope discipline — unrelated bug, flag for a future data-integrity pass, likely `data-agent`).

**Verdict for the design lead's gate question:** yes, genuinely end-to-end functional for the surface M1 actually implemented (chargen, the three monster-spawn paths, attack/damage/AC/HP/skills/flee/one blended-DC save-or-condition maneuver). No remaining gap was found that blocks M2 data batch-conversion from starting. The `initializeSavingThrows()` 6-key-vs-3-key gap and the four hardcoded `.con` call sites are real but non-blocking — they don't produce wrong numbers today, only latent fragility tied to CON/Vitality's current 1:1 bijection never changing.
