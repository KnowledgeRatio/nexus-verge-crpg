description: character.abilities is the ability-SCORE bag, never .find() on it — use CombatManager._findKnownAbility() to look up full ability definitions by ID
metadata:
  type: project

Fixed 2026-07-31: `attacker.character.abilities?.find(ab => ab.id === ...)` in `CombatManager.js` `attack()` (on-hit maneuver dispatch ~line 1248, and the old hardcoded Sworn Strike block ~line 1276) threw a TypeError on every confirmed hit, because `character.abilities` is `{str, dex, con, int, wis, cha}` — never an array. The `?.` optional chain only guards `abilities` being null/undefined, not `abilities.find` being missing on an object that exists.

**Why this had near-total blast radius but shipped anyway:** the throw happened *before* `attacker.consumeAction(actionType)` and `this.updateGameState()` (both fire later in the same function, ~line 1615+). Since `attack()` is called fire-and-forget (no `await`/`.catch()` at the UI call sites in `main.js`), the exception became a silent unhandled promise rejection — damage still applied and defeat still triggered (both happen *before* line 1248), but action consumption, HUD sync, Cleave/Harried/mastery post-hit effects never ran on any confirmed hit, for any attacker (player or monster). It went unnoticed because the one existing test file for this path (`combatManager.characterization.test.js`) was deliberately routed around the hit branch entirely.

**The fix:** `CombatManager._findKnownAbility(character, abilityId)` — checks `character.selectedAbilities?.includes(abilityId)` first (gate), then looks up the full ability definition from `window.game.abilitiesData.abilities[character.class?.id]`. This is the only path from an ability ID string to its full JSON definition (effects, actionType, etc.) at combat time — CombatManager does not load `abilities.json` itself.

**Adjacent finding, also fixed:** the Sworn Strike block called `window.game.promptSwornStrike(...)`, which does not exist anywhere in the codebase (only `window.game.promptVariableCostDamage` does — the generic ADR-010 replacement). That guard being permanently falsy is *why* the second `.find()` bug at that call site never fired in practice — the whole block was dead code. Replaced with a generic loop searching known abilities for `effects.variableCostDamage.trigger === 'onHit'`, calling the already-existing `promptVariableCostDamage` + the already-existing but never-wired `variableCostDamage` EffectDispatcher handler. This was a half-finished ADR-010 migration (handler + prompt existed, call site was never updated) — a pattern worth checking for elsewhere: a renamed/generic replacement function existing but the old call site still referencing the pre-rename name.

**Also required a second fix in the same block:** the on-hit maneuver dispatch context (passed to `dispatchAbilityEffects`) was hand-built without `addMessage`/`showFloatingText` — required unconditionally by `onHitSaveOrCondition`/`onHitCondition`/`onHitPush` handlers in EffectDispatcher.js. This was *also* masked by the `.find()` crash one line earlier (code that never ran can't expose its own bugs). Fixed by building the context via `EffectDispatcher.buildContext(character, combatant, combatManager)` and then manually adding `attacker`/`defender`/`resolveSpent` on top (those three are not part of the standard `buildContext` output and must always be added by the caller for on-hit handlers).

**Lesson for future characterization/bug-hunting passes on this file:** when a bug is found immediately upstream of other code, check whether that downstream code was *ever actually reached* before assuming it works — a crash one line earlier can mask an arbitrary number of further bugs in the same block. See [[adr010-ability-dispatch]] if that memory exists, otherwise see CLAUDE.md's ADR-010 section directly.
