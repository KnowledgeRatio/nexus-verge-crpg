Follow-up to [[attribute_remap_m1_formulas]]. Found and fixed 2 more gaps in the six-attribute remap (`docs/plans/2026-07-30-attribute-system-remap.md`), scoped a third. 411/411 passing after (up from 404). `RULES.attributes.system` still `'legacy'` by default — none of this is live until M1.5's flip. Full detail (exact skill table, exact code diffs reasoning) is in the plan doc's M1 step 7 section, appended 2026-08-01 — this memory is the durable "why/what to remember" layer, not a duplicate of that.

**Why this matters beyond the two named bugs:** this pass is the second time a hardcoded-6-legacy-keys pattern was found in more than one place after a prior pass believed it had been fully swept ([[attribute_remap_m1_formulas]]'s "370 passing masked 3 bugs" note was the first time). **Grep for the literal pattern `str: getAbilityModifier` / `str:.*,\s*dex:.*,\s*con:` whenever touching this system again** — don't trust that a prior pass caught every call site building an ability-modifier cache by hand.

**How to apply / key facts:**
- `Character.calculateAbilityModifiers()` was hardcoded to 6 legacy keys. Fixed generically: `Object.fromEntries(Object.entries(this.abilities).map(...))`. Same exact hardcoded pattern also existed at `EncounterBuilder.js`'s `createEnemyFromMonster()` and `Player.js`'s `generateDungeonEnemy()` (both building a monster's `abilityModifiers`) — fixed the same way at both. `Player.js`'s copy was *also* missing the six-attribute `abilities` merge entirely (`convertLegacyAbilitiesToSixAttribute`) — the M1 step 7 Bug-2 fix had only reached `Character.js` and `EncounterBuilder.js`, not this third monster-spawn path (`Player.js`'s dungeon-enemy generator, a separate code path from `EncounterBuilder.js`'s overworld/dungeon-pool encounter builder). **There are at least 3 independent places that construct an enemy/character object with ability data in this codebase — when fixing one, grep for the other two.**
- The real-world trigger for why the `calculateAbilityModifiers` bug mattered: `SkillChallengeManager.getSkillModifier()`'s sixAttribute-mode fix was the *first* live code in the whole codebase to read `character.abilityModifiers[newAttributeKey]` (e.g. `.composure`) directly — grepped and confirmed nothing else does. Everything else either reads the resolver (`getAttributeModifierFor`/`getBlendedAttributeModifier` in `attributeResolver.js`, which reads `character.abilities` directly, not `.abilityModifiers`) or reads a legacy key that stays populated in both modes. Worth remembering: `abilityModifiers` and the resolver are two different data paths that happen to overlap today — don't assume fixing one covers the other.
- `data/skills.json`'s skill->ability mapping **cannot** be derived by running the base score through `RULES.attributes.legacyToNew` — that table is for ability *scores*, and gives systematically wrong answers for skills (would send DEX-skills to Insight instead of Prowess, etc.). Skills needed their own explicit field. Added `attributeSixAttribute` per skill (dual-field, same convention as `kits.json`'s `abilitiesSixAttribute` — legacy `ability` field kept, new field added alongside). All 13 core skills came straight from the plan's decision #1 locked table. The 4 campaign-specific skills (`sailing`, `navigation`, `defiling`, `psionics`) weren't in that table — judgment calls: `navigation`/`defiling`/`psionics` (unsplit legacy `int`) → `intellect` (trivial, INT never splits); `sailing` (legacy `wis`) → `insight` by analogy to Perception/Cunning/Empathy (situational/reactive), not Composure. Flagged in the plan doc for review, same as decision #1 flagged Creativity→Composure as its most arbitrary call.
- **`SkillChallengeManager.getSkillModifier()` had 2 live bugs that predate and are unrelated to the remap**, only surfaced because doing Bug B properly required a real skill-check test rather than a resolver-in-isolation test (the exact lesson from [[attribute_remap_m1_formulas]]'s Bug 2 postmortem, applied a second time in this same session). `character.skills.find(s => s.id === skillId)` — `character.skills` is actually a dictionary keyed by skill id (`{ athletics: {proficient, expertise, bonus}, ... }`, see `Character.js`'s `initializeSkills()`), not an array; `.find` doesn't exist on it. `character.skillProficiencies.includes(...)` — that field is never populated anywhere in the codebase. Both would throw/crash on any real gameState character hitting a passive or active skill check in a conversational challenge. Fixed alongside the six-attribute field change: proficiency now reads `character.skills[skillId]?.proficient`; skill->ability lookup now reads a new `this.skillsData` array (loaded via new `SkillChallengeManager.loadSkillsData()`, wired into `main.js`'s existing `skillChallengeManager` init `Promise.all` alongside `loadChallenges()`/`loadTerrainChallenges()`) instead of expecting the data to live on the character object. **Lesson: when a task asks you to touch a function, check whether the function actually works against the real production data shape before writing "isolated" tests for your specific change — the resolver-in-isolation blind spot generalizes past just this migration.**
- Found but explicitly NOT fixed at the time (scope discipline — flagged in the plan doc instead). **Both of the first two were fixed in the very next session (2026-08-01, same day) — see below; don't treat "flagged, not fixed" as still current without checking the plan doc's status.**
  - `SettlementUI.js`'s `_skillToAbility()` — a third independent hardcoded skill->ability copy (UI-layer fallback used only when `window.skillChallengeManager` is unavailable). UI code, `frontend-dev` territory, wrong in sixAttribute mode today but not this pass's job to fix.
  - `Character.js`'s `updateSkillBonuses()`'s `skillAbilities` map — a *fourth* independent hardcoded skill->ability copy, computing `character.skills[id].bonus` for character-sheet display. Not producing wrong numbers yet (reads the legacy ability modifier, which stays correct in both modes as long as chargen is still legacy-only), but will silently drift once sixAttribute chargen/ASIs exist and new-attribute scores diverge from their legacy source. Forward-looking risk, not an active bug — same category as several other items already flagged-not-fixed in the plan.
  - `specializations.json`'s `primaryAttributes` — grepped, zero code consumers anywhere in `src/`. Confirmed pure flavor/descriptive metadata, no fix needed.
  - `practices.json`'s Hearthcraft `scoreChoices` (ability-bonus meal buff) — not a simple kits.json-shaped dual-field fix. It's a live interactive UI feature (`main.js`'s Hearthcraft modal) whose actual consumption path, `practiceUtils.js`'s `getBuffedAbility(character, abilityKey)`, has **zero production call sites** today (grepped — only its own unit tests exercise it). The ability-score portion of Hearthcraft is already dead/inert in production regardless of the remap; "fixing" it for sixAttribute mode would mean wiring up an unfinished feature end-to-end, not adding a parallel field. Scoped and reported, not touched.

**Both flagged loose ends closed 2026-08-01 (same day, follow-up task):**
- `SettlementUI._skillToAbility()` now delegates to `window.skillChallengeManager.skillsData` first (real `skills.json` data, dual-mode field read), falling back to a static dual-mode map only when `skillChallengeManager` itself isn't available. `RULES` had to be imported into `SettlementUI.js` for this (wasn't imported before — check before assuming a UI file already has rules-engine access).
- `Character.js`'s `updateSkillBonuses()` — investigated whether it could delegate to `skills.json` like the other two, and could **not**: `Character`'s constructor is fully synchronous top-to-bottom (`initializeSkills()` → `updateSkillBonuses()` runs inline during `new Character(...)`, no `init()`/async lifecycle at all), so a `fetch()`-based load isn't reachable at the point it's needed. No synchronous cross-environment JSON-loading mechanism exists anywhere else in this codebase either (no bundler-provided static JSON import, no shared preloaded-data singleton populated before first `new Character()` call) — this isn't a "didn't get to it" gap, it's a real architectural constraint specific to this one call site. Landed as a dual-mode hardcoded map instead (legacy vs. sixAttribute, switched on `RULES.attributes.system`, same values as `skills.json`), with an inline comment stating it must be hand-kept in sync. If a future pass wants true single-sourcing here, it needs either (a) converting `Character` construction to an async factory, or (b) a synchronous preloaded-skills-data singleton populated at game boot before any `new Character()` call — both are real architecture changes, not this-task-sized.
- Test precedent for UI-module tests in this fetch-less/DOM-less `node` vitest environment: stub `globalThis.document = { getElementById: () => null, querySelectorAll: () => [] }` (and `globalThis.window` for `window.skillChallengeManager`) before importing the UI module — same pattern already used in `tests/ui/CharacterCreation.sixAttribute.test.js`.
- 417/417 passing after this pass (up from 411), 6 new tests: 2 added to `character.characterization.test.js`'s existing sixAttribute block, new file `tests/ui/SettlementUI.skillToAbility.test.js` (4 tests, 2 legacy/sixAttribute delegation + 2 legacy/sixAttribute fallback-map).

**Test files touched this pass:** `tests/systems/character.characterization.test.js` (one new test in the existing sixAttribute Bug-2-regression describe block, verifying `abilityModifiers` — not just `abilities` — gets every key). New file `tests/systems/skillChallengeManager.sixAttribute.test.js` — built through a real `new Character(...)` and a real `SkillChallengeManager` populated from the actual `data/skills.json` via `readFileSync` (not a fetch mock, not a hand-built fixture). Uses Perception as the discriminating case: its legacy `ability` is `wis` but its `attributeSixAttribute` is `insight`, and `insight`'s legacy conversion source is DEX not WIS — so a character with divergent WIS/DEX scores produces genuinely different numbers depending on which field is actually read, proving the fix isn't a no-op. **Reusable pattern for any future skill/attribute test:** pick a skill whose legacy `ability` and `attributeSixAttribute` map to *different* legacy sources under the bijection (not just different names that happen to resolve to the same underlying score) — otherwise the test can pass even with the old buggy code.
