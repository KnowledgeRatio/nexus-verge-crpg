## Core rule
NEVER write `if (ability.id === 'X')` or `if (ability.effects?.specificName)` for a named ability. Register a handler by effect-type key in EffectDispatcher. `character.selectedAbilities` — array of known ability IDs (includes auto-granted, non-tactic abilities). Exemplar tactics are a SEPARATE array, `character.knownTactics` — see the "tactics vs selectedAbilities" bug below. NOT `character.abilities` (that's `{str, dex...}` — see [[fix-findknownability-bug]] for a bug caused by confusing the two).

## Terminology rename (2026-08-05)
"Maneuver" was renamed to "tactic" throughout (data-agent's `levelProgression.json`/`abilities.json` pass switched `choice.type` from `"maneuver"` to `"tactic"`; backend-dev's pass followed through in code). Renamed: `Character.getManeuverDie()`→`getTacticDie()`, `Character.knownManeuvers`→`knownTactics` (dual-read fallback per ADR-011: `data.knownTactics || data.knownManeuvers || []`), `Combatant.pendingManeuver`→`pendingTactic`, `EffectDispatcher.resolveManeuverDieSides`→`resolveTacticDieSides`, `rollManeuverDie`→`rollTacticDie`, `maneuverSaveDC`→`tacticSaveDC`, `main.js._isManeuverAbility`→`_isTacticAbility`, `LevelUpManager.renderManeuverChoice`→`renderTacticChoice`. DOM ids/classes (`maneuverChoiceSection`, `.maneuver-choice`, etc.) intentionally NOT renamed — frontend-dev territory, `data-choice-type` attribute value IS `'tactic'` now (functionally compared against `choice.type`), but the CSS-hook class name stays `maneuver-choice`. `ability.id === 'precisionStrike'` literal string checks are a pre-existing minor ADR-010 nit, deliberately left as-is (out of scope, only the *field* was renamed).

## Real production bug found during the rename (2026-08-05)
`CombatManager._findKnownAbility(character, abilityId)` checked only `character.selectedAbilities.includes(abilityId)`. But `Character.applyLevelUpSelections()` stores Exemplar tactics exclusively in `character.knownTactics` (a completely separate array, populated by a separate level-up choice path) — tactics are NEVER added to `selectedAbilities`. Result: the on-hit tactic dispatch at `CombatManager.attack()` (`this._findKnownAbility(attacker.character, attacker.pendingTactic)`) always returned `null` for every real character, so Trip/Menacing/Pushing/Disarming Attack's bonus damage + condition effect **never fired in production**, despite Resolve being spent and the UI showing the tactic as queued. Fixed: `_findKnownAbility` now checks `selectedAbilities` OR `knownTactics`. The existing characterization test (`tests/systems/combatManager.characterization.test.js`) had a hand-built fixture that set `selectedAbilities: ['testTrip']` directly instead of constructing through the real level-up path, which is exactly why this passed tests while being broken in real play — an ADR-015 "test through real construction, not hand-built fixtures" violation. Test now covers both the `selectedAbilities` path and the real `knownTactics`-only path explicitly.

## Pre-existing crash bug also found and fixed: LevelUpManager `currentSelections` reset omitted `tactics`/`maneuvers` key
`openLevelUpModal()` and `closeModal()` both reset `this.currentSelections` to a literal object that never included a `maneuvers`/`tactics` key (only the constructor's initial value had it). `toggleChoiceSelection()`'s checkbox branch does `this.currentSelections[`${choiceType}s`].push(choiceId)` with no optional chaining — so checking a tactic checkbox at level 3 threw a TypeError the instant the modal was opened for real (constructor's initial object gets overwritten by the reset on every `openLevelUpModal` call). All three `currentSelections` reset sites (constructor, `openLevelUpModal`, `closeModal`) must always carry the same key set.

## Level 7/9 tactic-choice visibility gap also found and fixed
The tactic section's visibility toggle only fired from `toggleChoiceSelection`'s specialization-radio click handler (level 3 only, where a `specialization` choice coexists with the tactic choice). At levels 7 and 9 there is no `specialization` choice that level (character already has a persisted `character.specialization`) — nothing would ever click to reveal the section, so the level 7/9 "Learn a Combat Tactic" choice would render its list but stay permanently `display: none`. Fixed in `renderChoiceSections`: the tactic section now shows immediately if `character.specialization` already matches the tactic choice's `requiresSpecialization`, falling back to hidden-until-clicked only when it doesn't (the level-3 case).

## EffectDispatcher Resolve Gate (implemented 2026-04-09)
- `execute()` has a single pre-dispatch Resolve gate: checks + deducts BEFORE any handler fires.
- Gate only fires when `ability.resourceType === 'resolve'` AND `!context.resolveAlreadyDeducted`.
- Cost priority: `ctx.resolveSpent` (variable-cost) > `ability.resolveCost` (number) > 1 (default).
- Returns `[{ type: '_resolveGate', result: { skipped: true } }]` and stops if insufficient Resolve.
- Handlers (`variableCostDamage`, `variableCostHeal`, `cureCondition`, `selfTempHP`, `allyTempHP`) are pure effect code — they never read or write `resolvePoints`.
- Tactic beforeAttack/onHit paths in CombatManager set `ctx.resolveAlreadyDeducted = true` when Resolve was already deducted at queue time in main.js (not dispatch time). Reaction tactics (Riposte, Parry) do NOT set this flag — their Resolve is deducted by the gate at dispatch time.
- `resourceType: 'shortRest'` abilities (Steady Nerve, Action Surge, **Indomitable**) are unaffected — the gate skips them entirely, so **shortRest usage tracking must be done manually by the caller** (see Indomitable below) — the gate is Resolve-only.

## Effect handler catalog
- `variableCostDamage` (EffectDispatcher): reads `ctx.resolveSpent` + `ctx.defender` (both must be injected manually by the caller — not part of standard `buildContext()` output). Config in JSON: `{ damageFormula, damageType, bonusVsCreatureTypes, bonusDice, trigger: "onHit", rangeType: "melee" }`. Dispatch wiring lives in `CombatManager.attack()`'s post-hit block — as of 2026-07-31 this searches `window.game.abilitiesData.abilities[character.class.id]` for abilities with `effects.variableCostDamage.trigger === 'onHit'` known via `character.selectedAbilities`, calls `window.game.promptVariableCostDamage(attacker, defender, ability)` for the Resolve-spend prompt, then dispatches via `EffectDispatcher.execute()` with `ctx.defender` and `ctx.resolveSpent` added on top of `buildContext()`.
- `variableCostHeal`: reads `ctx.resolveSpent` (injected by showAbilityChoices). Formula string e.g. `"resolveCost * conMod + level"` — evaluates via `Function()` after longest-first substitution.
- `cureCondition`: reads `ctx.resolveSpent` as fixed cost (1). Calls `combatant.removeCurableConditions()` limited to `count`.
- `rerollSavingThrow` (Indomitable, L2, both specs, new 2026-08-05): registered handler reads `ctx.combatant` (the reactor) + `ctx.saveAbility` (legacy key or new-system attribute name, same convention as `rollDefenderSave`), returns `{ newRoll, newTotal }`. Dispatched from `main.js promptReaction`'s new `'afterFailedSave'` hookPoint, called by `CombatManager.executeSpecialMonsterAction()` right after the original save-vs-DC message and before damage is rolled/halved. Since `resourceType: 'shortRest'` skips the EffectDispatcher gate, `promptReaction`'s eligibility filter AND its click handler both manually check/track `character.abilityUses[ability.id]` vs `usesPerShortRest` (same pattern `canUseAbility`/`trackAbilityUsage` already use elsewhere in main.js) — this is NOT automatic like the Resolve gate.
- `exposedPassive` / `vanguardsChargePassive` (markers, no EffectDispatcher handler registered — checked via `character.selectedAbilities.includes('exposed'|'vanguardsCharge')`, matching the convention `LevelUpManager.confirmLevelUp`'s `autoGrantAbilities` already uses to grant them):
  - **Exposed** (L3, Exemplar): `rollDefenderSave(defender, saveAbility, { disadvantage })` now supports disadvantage (roll-twice-take-lower, mirrors `CombatManager.attack()`'s own advantage/disadvantage pattern). `checkExposedDisadvantage(attacker, defender)` (module-private in EffectDispatcher.js) finds a condition on `defender.conditions` where `appliedBy === attacker.id && inflictedByTactic && !exposedConsumed`. All three save-or-condition handlers (`onHitSaveOrCondition`, `onHitCondition`, `onHitPush`) call it before rolling the save, and set `sourceCondition.exposedConsumed = true` via **direct object mutation** (not through `addCondition`'s options) — this sidesteps `addCondition`'s stacking guard entirely (reapplying the same condition `type` returns `false` without updating the existing entry's fields; consumption-tracking would silently break if it were threaded through that call instead of mutated directly). Explicitly tested (`tests/systems/dedicationLevel2to9.test.js`): different condition types both proc fine; same-type reapplication (Trip Attack twice on an already-prone target) confirms the addCondition no-op happens (still only 1 `prone` entry) but `exposedConsumed` still persists correctly. `Combatant.addCondition()` now accepts/stores an `inflictedByTactic` option (generic marker, ADR-010 compliant — not tied to any tactic name), set `true` by all three save-or-condition handlers on successful application.
  - **Vanguard's Charge** (L5, Exemplar): in `CombatManager.attack()`, `targetWasUnengaged = defender.engagedWith.size === 0` MUST be read before the melee engagement-mutation block (`attacker.engagedWith.add/defender.engagedWith.add`) runs later in the same function — captured early (right after `disarmedPenalty`, well before that mutation point) since the resulting `+1` bonus needs to feed into `attackTotal`, which is computed before the mutation block anyway. Gated on `!isRanged && targetWasUnengaged && attacker.team==='player' && attacker.pendingTactic && selectedAbilities.includes('vanguardsCharge')` — `!isRanged` restriction is a backend-dev judgement call (engagement is a melee-only concept in this codebase; ranged attacks never touch `engagedWith`), not explicitly required by the design brief.
- `allyTempHP` (Rally's ally option, new 2026-08-05): **scoped down deliberately** — no multi-ally target picker exists (or was built) anywhere in this codebase. Targets the first `combatManager.companionCombatants` entry with `engagedWith.size > 0`; no-ops with a message if none. Revisit if/when the party system supports multiple simultaneous engaged companions and picking between them becomes meaningful.
- `showAbilityChoices` (combat) and `showOutOfCombatAbilityChoices`: expand `variableCostHeal` options into per-resolve-spend buttons; pass `data-resolve-spend` attribute. `executeAbilityChoice` / `executeOutOfCombatChoice` injects `context.resolveSpent = resolveSpend`.
- `LevelUpManager.confirmLevelUp`: after `applyLevelUpSelections`, reads `specializationFeatures[specKey].autoGrantAbilities` from progression data and pushes to `character.selectedAbilities` — `specKey = this.currentSelections.specialization || character.specialization` (fixed 2026-08-05: levels with their own `specializationFeatures` but no specialization *choice* that level, e.g. L5's Vanguard's Charge, previously never granted anything because `currentSelections.specialization` is only populated the level the choice itself appears). Also reads `newFeatures[].grantedResource` and sets `character.max{Id}Points`, `character.{id}Points`, `character.{id}Recharge` generically from data.
- `aidTheVulnerable` uses `effects.choice` + options — routes through `showAbilityChoices` / `executeAbilityChoice` (same as Steady Nerve, and now Rally's self/ally choice). No inline modal.

## ADR-010: Exemplar Tactic System (migrated 2026-04-09, renamed from "maneuver" 2026-08-05)
- All 8+ Exemplar tactics in abilities.json use typed effect keys — the old `"maneuver": "tripAttack"` pattern is gone.
- Effect type → tactic mapping: `precisionAttackBonus` (Precision Strike), `onHitSaveOrCondition` (Trip Attack, Menacing Attack), `onHitPush` (Pushing Attack), `onHitCondition` (Disarming Attack), `selfTempHP`/`allyTempHP` (Rally's two options), `reactionAttack` (Riposte), `reactionDamageReduction` (Parry), `rerollSavingThrow` (Indomitable, not Exemplar-gated — both specs).
- EffectDispatcher.js handlers: `resolveTacticDieSides(character)` — L3-6=d6, L7-9=d8, L10+=d10. `tacticSaveDC(character, config)` — default `8+prof+getAttributeModifierFor(character,'meleeAttack')` (Prowess-only, legacy mode redirects to STR); `config?.dcContext` + `RULES.attributes.system==='NVSystem'` overrides to a blended context (Menacing Attack only). Both are module-level helpers, not exported.
- All on-hit handlers (`onHitSaveOrCondition`, `onHitCondition`, `onHitPush`) require `ctx.attacker` and `ctx.defender` injected by CombatManager (NOT in standard `buildContext()` output — must be added manually).
- `precisionAttackBonus` handler returns `{ bonus: N }` — CombatManager reads `result.bonus` to add to attackTotal.
- `selfTempHP`/`allyTempHP` handlers consume bonusAction internally — Resolve is deducted by the pre-dispatch gate in `execute()`, not inside the handler.
- `reactionAttack` / `reactionDamageReduction` / `rerollSavingThrow` return their roll result — `promptReaction` in main.js dispatches them via EffectDispatcher and reads `result.bonus` / `result.damageReduction` / `result.newTotal` to act on.
- The full ability lookup for a queued `pendingTactic` ID is `CombatManager._findKnownAbility(character, abilityId)` (reads `window.game.abilitiesData.abilities[class.id]`, gated on `character.selectedAbilities` OR `character.knownTactics` — see the real bug fixed above). Do not assume a differently-named helper exists — check the file directly.
- main.js: `_isTacticAbility(ability)` helper — returns true when any tactic effect key is present in `ability.effects`. Used everywhere `ability.effects?.maneuver` was previously checked.

## Third save implementation had no afterFailedSave hook (fixed 2026-08-06)
There are three independent save-vs-DC implementations in the codebase: `EffectDispatcher.rollDefenderSave()` (tactic handlers), `CombatManager.executeSpecialMonsterAction()`'s inline save, and the Topple weapon-mastery inline save in `CombatManager.attack()` (~line 1575, inside the `hasWeaponMastery(attacker, weapon, 'topple')` onHit block). Only the second had the `afterFailedSave` reaction hook (`window.game.promptReaction('afterFailedSave', attacker, defender, { saveType, saveDC, saveRoll })`) wired in — Topple's save was a complete gap, so Indomitable could never fire off a failed Topple save. Fixed by wiring the identical hook call into Topple's block, same signature/pattern, nothing unified. Deliberately did NOT touch `rollDefenderSave()` or attempt to merge the three implementations — that unification is a separate, larger effort tracked elsewhere. When adding a new save-vs-DC check anywhere in combat, check whether it needs this same reaction hook — it is easy to add a fourth ungated save site by copy-pasting an old block instead of routing through one of the two hook-aware patterns.

## abilityUses reset must be resourceType-aware (fixed 2026-08-06)
`Character.shortRest()`/`longRest()` (class methods, currently NOT used by the live player rest flow — see below) track ability use-counters in `this.abilityUses` keyed by ability ID, but the ability's `resourceType` (`'shortRest'` vs `'longRest'`, from abilities.json) determines which rest type clears it. `resourceType: 'resolve'` abilities do NOT use `abilityUses` at all — Resolve is a separate point pool (`resolvePoints`/`spendResolve`/`restoreResolve`), checked via `character.resolvePoints`, not `abilityUses[id]` (confirmed by reading `main.js canUseAbility`/`getAbilityUsesText`, which already branch on `resourceType` correctly for `shortRest`/`longRest`/`resolve` separately). Fix added `Character._getKnownAbilityDefinitions(abilitiesData)` (mirrors `CombatManager._findKnownAbility`'s lookup: `window.game.abilitiesData.abilities[class.id]`, gated on `selectedAbilities` OR `knownTactics`) and `_resetAbilityUsesByResourceType(resourceTypes, abilitiesData)`, both accepting an optional `abilitiesData` param for test injection (Character.js has no async data loading of its own). `shortRest()` clears only `['shortRest']`; `longRest()` clears `['shortRest', 'longRest']` (a long rest also resets short-rest resources — standard 5e).

**Found while fixing this**: `Character.shortRest()`/`longRest()` are dead code for the actual player rest flow — `RestManager.js` (the real in-game rest path, singleton `restManager`) reimplements HP/hit-dice/spell-slot recovery directly against the plain `gameState.get('character')` object and never calls the `Character` class methods, and never touches `abilityUses` at all. So in current live play, short-rest/long-rest-gated ability use-counters are never reset by either rest type — a separate, real gap from the one this task fixed, left unaddressed since it was out of scope (task was Character.js only). Flag this if `RestManager.js` is touched next — it needs the same `abilityUses` reset logic RestManager.js is missing entirely, not routed through the now-fixed-but-uncalled `Character` methods.

## CRITICAL LIVE BUG found 2026-08-06, NOT fixed (characterized only, per task scope): `promptReaction()` crashes for every real character
`Game.promptReaction()` (`src/main.js`, the only reaction-dispatch code in the game — Riposte/Parry/Indomitable all route through it) reads `character.abilities` and calls `.filter()` on it directly to build the eligible-reactions list. But `character.abilities` is ALWAYS the six-score ability bag (`{str,dex,con,int,wis,cha}`, set by `Character.calculateAbilities()`) on every real character produced by chargen/level-up — never an array of ability definitions. Known abilities live in `character.selectedAbilities`/`character.knownTactics` (ID-string arrays), which must be resolved against `window.game.abilitiesData` — exactly what `CombatManager._findKnownAbility()` does elsewhere, but `promptReaction()` never does this resolution. Result: `abilities.filter is not a function` throws unconditionally for every real player character with a reaction available, before any per-hookpoint (afterMiss/afterHit/afterFailedSave) logic runs. **Riposte, Parry, and Indomitable are completely non-functional in live play today, regardless of whether the character knows them.** This is the exact same bug pattern as the previously-fixed `_findKnownAbility` bug ([[fix-findknownability-bug]]) — never applied here. Characterized (not fixed, out of scope for that task) in `tests/systems/promptReaction.characterization.test.js`, section B, using real `Character` construction deliberately (not a fixture that fakes `character.abilities` as an array, which would mask the bug the same way a prior fixture masked `_findKnownAbility`'s). **Must be fixed before or as part of any work that touches `promptReaction()`** — including the planned generalization to fire reactions on an ally's behalf.

## promptReaction() coverage landscape (as of 2026-08-06)
Prior to this date, `promptReaction()` had ZERO direct test coverage — every existing call site test (`combatManager.characterization.test.js`'s Topple test) mocks `window.game.promptReaction` itself rather than exercising the real implementation. `tests/systems/promptReaction.characterization.test.js` closes this: (A) pre-eligibility gating (team check, no-reaction-available check — both run BEFORE the crash above and are real/working), (B) the crash itself, (C-E) EffectDispatcher-level dice/Resolve-gate math for `reactionAttack`/`reactionDamageReduction`/`rerollSavingThrow` using real ability objects pulled from `data/abilities.json` (not hand-typed effect configs), (F-H) CombatManager-boundary consumer tests (`attack()`'s afterHit/afterMiss hooks, `executeSpecialMonsterAction()`'s afterFailedSave hook — the second of the two live afterFailedSave call sites, Topple being the first) with `window.game.promptReaction` mocked at the return-value boundary, the same accepted pattern the existing Topple test already used. Two secondary findings from writing this: real weapon fixtures must use `damage: '1d8'` (string), not `{dice:'1d8'}` — see [[combat-weapon-damage-shape-bugs]]; `data/abilities.json`'s `abilities` key is `{ description, dedication, wanderlust, scholar }` where each calling is a flat array (not keyed by class id further), so a lookup helper must skip the `description` string key.

## Also found (not characterized, not fixed): Riposte's counter-attack call passes the wrong option key
`promptReaction()`'s Riposte click handler calls `cm.attack(defender, attacker, 'mainHand', { shouldConsumeAction: false, extraDamage: dieRoll })`, but `CombatManager.attack()` reads `options.consumeAction` (not `shouldConsumeAction`) to decide whether to consume the attacker's action — confirmed by direct probe (defender.actions.action went from 1 to 0 after a Riposte counter-attack). So Riposte's "free" counter-attack silently consumes the reactor's Action too, not just the Reaction. Not added to the official characterization suite because reaching this code path requires bypassing the eligibility-filter crash above with a hand-faked `character.abilities` array — the exact fixture-masking anti-pattern ADR-015 warns against — so it's recorded here instead, for whoever fixes the crash bug to check this too. Also found empirically: because the EffectDispatcher Resolve gate silently skips (returns `_resolveGate`) rather than promptReaction checking Resolve upfront, Riposte/Parry currently still consume the Reaction and (for Riposte) still execute a real counter-attack even with 0 Resolve — the gate only zeroes the bonus die, it doesn't block the reaction from firing. This IS covered by the official suite (section C/D's "insufficient Resolve" tests, at the EffectDispatcher level) but is worth remembering as a design gap: "doesn't fire if... insufficient Resolve" (a stated requirement in at least one task brief) is not what the current code does.
