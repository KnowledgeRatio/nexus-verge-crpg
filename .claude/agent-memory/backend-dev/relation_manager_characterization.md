## What this covers
`tests/systems/RelationManager.characterization.test.js` (2026-08-07), written per ADR-015 before a faction-contribution hook lands inside `modifyRelation()` (`src/systems/RelationManager.js`). Prior coverage (`RelationManager.tradingPractice.test.js`) was scoped narrowly to Trading practice's buy/sell pricing math only. New suite locks down: `modifyRelation()` clamping at +/-100, history trim to `historyMaxLength` (currently 20, from `data/relations.json`), random-range rolling via `Math.random` mocking (established pattern: `vi.spyOn(Math, 'random').mockReturnValue(...)`, not a custom RNG), `getRelation()`'s baseline with `_getFactionModifier()` as its current always-0 placeholder (explicitly asserts `effectiveScore === personalScore` even when `gameState.data.factions` is populated — this is the "before" snapshot the real faction hook must not silently break for personal-relation-only behavior), tier-boundary edges built **data-driven off `relations.json`'s own tier array** (`it.each` over adjacent tier pairs, not hardcoded numbers) so the test stays correct if tier boundaries are retuned, and the three gating methods (`canOfferQuest`/`canTrade`/`canSpeak`) at those boundaries. Real call site coverage: `MerchantManager.buyItem`/`sellItem` end-to-end through `window.game.relationManager` (both call `modifyRelation(npc, 'successfulTrade')`), plus a fallback-path test confirming relations are untouched when no relationManager is present.

## Test-env gotcha: `window` is not defined in this project's vitest config
`vitest.config.js` sets `environment: 'node'` globally (no jsdom) — `window` does not exist by default. The established fix, copied from `tests/systems/promptReaction.characterization.test.js`, is a per-file polyfill at module scope: `globalThis.window = globalThis.window || {};` before any `beforeEach` that does `window.game = ...`. Do this in any new test file that touches `window.game` (which is how most systems reach their singleton managers, e.g. `window.game?.relationManager`).

## gameState singleton leak pattern
`RelationManager.js` imports the real singleton `gameState` module-level (not injected) — same as most systems. Per this task's instruction (a preventive pattern, not yet load-bearing): reset `gameState.data.factions = {}` in `beforeEach` even though `_getFactionModifier()` doesn't read it yet, so the pattern is already in place before the real faction hook starts writing to `gameState.factions` and could leak state across test cases in the same file.

## FIXED 2026-08-07: `world.generatedRegions` Map-vs-plain-object mismatch
The bug flagged below as "found but not fixed" was fixed same-week. All three sites — `RelationManager.modifySettlementRelations()` (~line 188), `QuestManager._findNPCById()` (~line 891), `DialogueManager.getDynamicLines()` (~line 271) — did `for (const regionKey of Object.keys(world.generatedRegions)) { const region = world.generatedRegions[regionKey]; ... }`. Both halves were broken on a real `Map`: `Object.keys(aMap)` is always `[]`, and `aMap[key]` bracket access is always `undefined` even if the keys loop somehow worked. Fix at all three (identical shape since `regionKey` was unused in any of the three loop bodies — verified by reading each body in full before fixing, per ADR-015's "read each call site's actual usage before choosing the fix shape"): replaced the whole two-line pattern with `for (const region of world.generatedRegions.values()) { ... }`. No grep hits remained for `Object.keys(...generatedRegions...)` after the fix (checked codebase-wide, not just the three known sites).

Real end-to-end test added in the "generatedRegions Map lookup bug fix" describe block in this same file: builds `world.generatedRegions` as a real `new Map()` (not a plain object standing in for one — that distinction is the entire bug), runs `QuestManager.completeQuest()` through to `_findNPCById()` → `RelationManager.modifyRelation()`/`modifySettlementRelations()`, and separately exercises `DialogueManager.getDynamicLines()` finding a nearby dungeon feature. Confirms quest-completion relation/faction changes are now actually reachable in real play — previously the lookup failed silently before `modifyRelation()` was ever reached, so the faction-contribution hook (see `modifyRelation() — faction contribution hook` tests above) had no real input path despite testing green in isolation.
